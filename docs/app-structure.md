# App structure

[日本語](app-structure.ja.md) · [README](../README.md#documentation)

How a lamina-ui program runs: the window and its frame loop, the input it receives, and the pieces that route input, focus and accessibility between widgets. A minimal program is in the [README](../README.md#a-minimal-program).

## Targets and input events

The library is three CMake targets, each in its own directory under `src/`. The backends' aliases `lamina::thorvg` and `lamina::sdl3` are also their namespaces, and the core's namespace is `lamina`. `src/lamina/` is the core (`lamina::lamina`: tokens, color, the canvas interface, text, shapes, layout, input events and widgets) and uses neither SDL3 nor ThorVG. `src/lamina_thorvg/` is the canvas drawn by ThorVG (`lamina::thorvg`), and `src/lamina_sdl3/` is the window, the preference directory and the system fonts (`lamina::sdl3`). The two backends depend only on the core, not on each other. Widgets take pointer, key and text events and a clipboard from `lamina/input/` (`lamina::input`); the SDL3 window produces them. `input::Key` names the editing keys, the letters, the digits and the characters `+ - * / . % = ( ) ^ !`, and the space bar (`Key::space`, which the window reports as a named key like Enter, so `key_for_character` leaves the space character unmapped), and Page Up and Page Down (`Key::page_up`, `Key::page_down`). `input::WheelEvent` is one turn of the mouse wheel at the pointer, in notches (a touchpad gives fractions); a positive `dy` scrolls toward the end and a positive `dx` to the right, also when the system flips the wheel's direction; `ctrl` says whether Ctrl was held (off while Alt is held too). The window collects them in `Frame::wheel`. `input::FingerEvent` is one finger on a touch screen: its id, `down`, `move`, `up` or `cancel`, the point in dp and the time. The window collects every finger in `Frame::fingers`, from SDL's finger events, converting the position as SDL does when it makes mouse events for the first finger, so that finger and its pointer events agree; SDL's own touch events made from the mouse or a pen are left out. The pointer events still carry the first finger as a touch, which is all most widgets need; a widget that follows several fingers, such as `ZoomView`, reads `Frame::fingers`. The window reports a character key by the character it types with the Shift state held at that moment (`input::key_for_character`), so `*` is Shift+8 on a US layout and Shift+: on a Japanese one; the numeric keypad gives the same keys. Character keys arrive as key events without turning on text input, so an IME in kana mode does not catch them. `input::character_for_key` goes the other way, from a letter, digit or character key to the character it names (lower case for letters). A `KeyEvent` carries the Shift, Ctrl and Alt states (`shift`, `ctrl`, `alt`); `ctrl` is off while Alt is held too, since Ctrl+Alt is AltGr on some layouts. A `PointerEvent` says whether it came from a mouse, a touch or a pen (`kind`); the window takes it from SDL's touch and pen mouse IDs. `PointerEvent::waiting_scrollers` names the axes of the scroll areas around a widget that are waiting for a touch drag to pass the slop, so a scroller inside can leave a drag at the wrong angle to them. `PointerEvent::margin_claimed` says that another control has taken the point in its touch target, so the widget hit-tests only its own bounds ([Touch target](design-tokens.md#touch-target)). The window holds back the mouse moves that Windows sends to the cursor a touch left behind (`input::TouchEchoFilter`), so the control under the last touch does not show hover until the mouse really moves ([Mouse echoes after a touch](design-tokens.md#mouse-echoes-after-a-touch)). A touch that the system takes back never clicks: SDL makes a plain left-button release from a cancelled finger (`SDL_SendTouch` in SDL 3.4.10 sends the release for `SDL_EVENT_FINGER_CANCELED` as for `SDL_EVENT_FINGER_UP`, before the finger event), so the window holds each touch release until the first finger's own up or cancel arrives (`input::TouchReleaseGate`) and then passes `up` and `leave` for a lift, or only `leave` for a cancel, which every widget already treats as the pointer going away without a click. A release whose finger event never comes is passed on after one frame. This is what an Android edge swipe for Back produces: the app gets the touch until the system takes it with `ACTION_CANCEL` ([Android](android.md#what-works)). Inside the core, `tokens/` depends on the modules whose values it fills (`motion::SpringSpec`, `text::TextStyle`, `color::Role`, `render::CornerRadii`), and `motion/`, `text/`, `color/` and `render/` do not depend on `tokens/`.

## Frame loop

`lamina_sdl3/app.hpp`: `run_app` runs the frame loop on that window. Each frame it calls `update` with the frame (input, size, time step), which returns the background color; clears the canvas to it and scales it to dp; calls `paint`, which draws and returns whether anything is still animating; and presents. While nothing animates, the next frame waits for an event. So `update` lays the content out again after it has handled the input: a handler that changes content, such as `Label::set_text`, only marks it to be measured at the next layout, and a frame that ends with nothing animating would otherwise show the old content until the next event. A touch tap whose down, up and leave arrive in one frame is such a frame, since the press and hover state layers never start to move. The gallery and the text field example lay out before and after the input. On Windows, dragging the window's border runs a modal loop inside the system, so a loop that pumps events would stop drawing until the mouse is released and the layout would then jump to the new size; `run_app` therefore also draws a frame (with no input) from each live-resize expose event SDL sends during the drag (`Window::on_live_resize`), so the content follows the border. One overload creates the window from `WindowOptions` and a canvas, the other takes an existing `Window` for programs that use it inside the callbacks (the clipboard, `set_text_input`, `wake_after`). `run_app` does not catch exceptions: they reach the caller, which decides how to report them, and the same handler covers the setup before the loop, such as loading fonts. The `Window` methods stay available for a loop of your own.

## Window

`lamina_sdl3/window.hpp`: an SDL3 window that shows a canvas, converts pointer input to dp, and waits for events while nothing is animating (`lamina::sdl3`). A frame's time step is capped at 0.1 s, except after a wait that `wake_after` asked for: that frame's step covers the time slept, so a countdown kept in `step`, such as the text field's caret blink, moves on while the window idles. The window does not depend on ThorVG: it takes the canvas it draws on as a `std::unique_ptr<render::Canvas>`, resizes it to the window's size in pixels with `Canvas::resize` each frame, and uploads the pixels that `Canvas::finish` returns as 32-bit ARGB, so any canvas that renders into ARGB pixels can be plugged in. `set_size(width, height)` resizes the window's content area to a size in dp, restoring it first when it is maximized, and `set_minimum_size` keeps the user from dragging it smaller than a size in dp; both convert dp with the display scale, as the constructor does. `set_always_on_top` keeps the window above other windows. `set_dark_system_bars(dark)` makes the status and navigation bar icons light over a dark app and dark over a light one on Android and does nothing elsewhere, and `system_dark_theme()` says whether the system is in dark mode ([Android](android.md#system-bars)). On Android the system Back arrives as `Key::escape` with `KeyEvent::back` set; a program that did not use it calls `system_back()`, which hands it to the system and, for a root activity, sends the app to the back ([Android](android.md#back)). Elsewhere `KeyEvent::back` is false and `system_back` does nothing. `native_handle` returns the window's `HWND` on Windows (null elsewhere) for platform code. The examples pass a ThorVG canvas made by `examples::window_canvas()` (`examples/common/canvas.hpp`). `Frame::safe_area` is the part of the window that system bars and display cutouts leave free, as insets in dp; it is zero on the desktop. On Android it comes from the activity (`systemBars | displayCutout`) instead of SDL's safe area, which also holds the system gesture insets ([Insets](android.md#insets)). `Frame::gesture_insets` are the system gesture areas, for keeping edge drags away from them, not for layout; they are zero on the desktop and below Android 11. `lamina/layout/safe_area.hpp` has the conversions (`safe_area_insets`, `insets_in_dp`) and `inset_rect`, and the gallery lays itself out inside the safe area.

## Canvas

`lamina/render/canvas.hpp`: a 2D canvas with paths, rounded rectangles, drop shadows and a transform stack, drawn by ThorVG (`lamina::thorvg`). Why ThorVG: [docs/renderer-comparison.md](renderer-comparison.md). `fill_rect` fills a plain rectangle, and each backend implements it. The ThorVG canvas gives it the same outline as a rectangle path rather than `appendRect`, because ThorVG fills a four-cornered axis-aligned outline without anti-aliasing and the edges would change. `draw_image(image, rect, opacity)` draws a `render::Image` (`render/image.hpp`: a width, a height and the pixels row by row as ARGB with straight, not premultiplied, alpha) stretched to fill a rectangle, under the transform and the clip, at an opacity from 0 to 1, as Compose's `DrawScope.drawImage` with a destination size and an alpha does. The ThorVG canvas copies the pixels when it is called, so the image does not need to live until the frame is drawn, and scales them with bilinear filtering; a retained image drawn on the GPU is the exception ([Retained images on the GPU](#retained-images-on-the-gpu)). `push_clip` takes a rectangle or any path, as Compose's `Modifier.clip(shape)` does, so an image can be cut to one of the Material shapes; `pop_clip` ends the latest one, and clips nest. `render/geometry.hpp` has the point arithmetic (`+`, `-`, scaling, `length`, `unit`, `left_normal`, `cross`) and `circle_rect`; `render/path.hpp` builds rounded rectangles, rings for outlines (`ring_path`), circles (`circle_path`) and the outline of a line of points with round caps (`stroke_path`), since the canvas only fills.

What the canvas leaves out: it keeps the bounding box of the clips (a rectangle clip, or the bounding box of a path clip, under the transform, each intersected with the one around it; `visible_bounds()`), and `quick_reject(rect, outset)` says whether a rectangle in the current coordinates, grown by `outset`, falls wholly outside them or outside the canvas. `fill_path`, `fill_rect`, `fill_rounded_rect`, `fill_shadow` (grown by the offset and `shadow_margin_sigmas` times the blur) and `draw_image` test the bounding box of what they draw before transforming it and do not hand it to the backend when it is outside; `text::draw_line` and `IconFont::draw` test the line's or the icon's box (grown by `cull_glyph_outset_em` of the size) before building the glyph outlines. A program can call `quick_reject` itself to skip whole parts. Since the whole page of a scroll area is painted each frame, most of a long page is skipped this way.

The ThorVG canvas draws each blurred shadow from a cache: the first time a shape is shadowed, it blurs it (ThorVG's Gaussian blur at `shadow_quality`) into an image of its own, `shadow_margin_sigmas` standard deviations larger on each side, and from then on draws that image, which is a plain copy of pixels instead of a blur. The key is the shape relative to its top left corner, rounded to `1 / shadow_shape_steps` px, with the blur and the color, so a shadow that only moves, as on a scrolling page, is blurred once. The image is drawn at the nearest whole pixel, so a shadow can be up to half a pixel from where its surface's fractional position would put it; drawing it at the exact position would send ThorVG through its scaled-image path. The cache drops the least recently drawn images beyond `shadow_cache_bytes`, never one drawn in the current frame. ThorVG runs with worker threads, one fewer than the cores and at most `worker_threads_max` (`reserved_cores` is the one left for the main thread). The tokens are in `lamina/tokens/raster.hpp`.

## Damage tracking

A program paints the whole window every frame, but in most frames little of it changes: a scroll moves the list and not the bars around it, a pressed button changes its own pixels, and a photo that moves is drawn by the GPU, not ThorVG. The canvas therefore rasterizes and the window uploads only the parts of layer 0 (the full-window ThorVG buffer) whose drawing changed since the last frame.

How it works:

- The window is cut into square tiles of `damage_tile` px (`render::DamageGrid`, `lamina/render/damage.hpp`). Every call that reaches layer 0 (the background of `clear`, `fill_path`, `fill_rect`, rounded rectangles, `fill_shadow`, `draw_image` drawn by ThorVG, and so text and icons) is hashed (`render::Fingerprint`) from what decides its pixels: the kind of call, the points after the transform, the color and fill rule, the shadow's offset, blur and color, the image's transform, opacity, size and either its identity or, without one, its pixels, and a hash of the clips around it (each rectangle or path after the transform, outer to inner). The hash is folded into every tile under the call's bounding box, grown by `damage_outset` px for antialiasing (and one more pixel for a shadow, which is placed at a whole pixel) and cut to the clips and the canvas, in drawing order.
- At `finish`, a tile whose fingerprint differs from the last finished frame is dirty. A call that moved changes the tiles it left and the tiles it entered, so both the old and the new bounds are repainted. A call that moved into a layer above a retained image leaves layer 0, and its old tiles are repainted without it. Calls in upper layers and retained images on the GPU are not part of layer 0's fingerprints; each upper layer has a grid of its own (below).
- Dirty tiles are merged into rectangles: runs along each row, then runs of the same columns down the rows, then, beyond `damage_rects_max` rectangles, the pair whose union adds the least area, again and again (more than `damage_merge_input_max` runs are merged into their bounding box at once). For the ThorVG canvas a run is always the whole row (`Canvas::repaints_whole_rows`, `DamageSettings::whole_rows`), so the rectangles are bands across the full width. ThorVG's CPU blender fills a translucent span one pixel at a time up to its first 16-byte-aligned pixel and after its last whole group of four, and four pixels at a time in between (`tvgSwRasterAvx.h`); the one-pixel blend rounds as `(c × (a + 1)) >> 8` and the four-pixel one as `(c × a + 255) >> 8`, so the same pixel can come out one level apart. A rectangle that cut spans at its left or right side moved where those runs start and end and changed up to three pixels next to the side (found by `components_capture --verify-repaint` under a dialog's scrim, in a canvas 1081 px wide, whose rows start at different alignments). With whole rows every span is the same as in a full repaint; leaving rows out did not change the other rows in any comparison (the tests and the `--verify-repaint` scenes). When `damage_full_fraction` of the tiles or more are dirty, the whole canvas is repainted.
- The ThorVG canvas builds the frame's scene exactly as before, into a scene of its own for layer 0, and rasterizes it once per band with `SwCanvas::viewport` set to the band, so ThorVG fills only those rows; the rest of the buffer keeps the last frame. The background of `clear` covers a rectangle when it is opaque; when it is not, the rectangle is first set to zero. The canvas is made with `EngineOption::None`, so ThorVG's own partial rendering, which would clear the boxes of the paints it saw change, stays off, and it draws with `draw(false)`: ThorVG's `draw(true)` clears the whole buffer whatever the viewport, which, with the background that `clear` fills, used to write every pixel twice a frame.
- The rectangles repainted since the window last asked are kept (`Canvas::take_changed_pixels`; beyond `damage_pending_max` they are merged into one), and `sdl3::Window::present` uploads only those parts of the texture, one `SDL_UpdateTexture` each, with the buffer's stride. Upper layers are cut to their content and tracked the same way, each with its own grid in its own pixels: a layer whose pixel bounds are the same as in the last frame keeps its buffer, has the bands of its changed tiles set to zero (it is translucent) and repainted with `SwCanvas::viewport` and `draw(false)`, whole rows of the layer as for layer 0, and reports them in `UpperLayer::changed` (in window pixels, kept until `take_changed_pixels`); the window uploads only those into the layer's texture. A layer is repainted and uploaded whole when its bounds change, when it was not drawn in the last frame, after `resize` or `invalidate`, while damage tracking is off, and when the window makes its texture or uploads everything after a reset. Before this, every upper layer was repainted and uploaded whole each frame, so a scrim over a playing video, which puts the whole window in layer 1, cost a full-window ThorVG fill and a 10 MB upload for every video frame (about 9 ms of work per frame in landscape on the emulator, against under 2 ms without it).

The whole canvas is repainted in the first frame, after `resize` (a new size or density), after `Canvas::invalidate()`, and in every frame while damage tracking is off. The window uploads the whole texture when it makes the texture (the first frame, a new size, a lost device) and after `SDL_EVENT_RENDER_DEVICE_RESET`, `SDL_EVENT_RENDER_TARGETS_RESET`, `SDL_EVENT_WINDOW_RESTORED` and `SDL_EVENT_DID_ENTER_FOREGROUND`, in case the GPU lost its contents. A theme switch changes the colors and so every tile; an animation changes the tiles it draws in.

To force a full repaint, for checking that damage tracking draws the same pixels or for comparing times:

- `WindowOptions::damage_tracking = false` at start, or `Window::set_damage_tracking(false)` at any time; `Canvas::set_damage_tracking` on a canvas without a window, as in the tests and the capture tool. The default is `damage_tracking` in `lamina/tokens/raster.hpp`.
- The environment variable named by `full_repaint_environment` (`LAMINA_FULL_REPAINT`), set to anything but `0` or empty, turns it off for every window of the process.
- The components example takes `--full-repaint`, and `components_capture` takes `--full-repaint` and `--verify-repaint` ([testing](testing.md)).

The counts in [frame timing](#frame-timing): `repaint tiles` (the dirty tiles of layer 0 and the upper layers; every tile of a layer repainted whole), `repaint Mpx` (the pixels of the rectangles ThorVG rasterized in layer 0 and the upper layers) and `canvas up Mpx` (the pixels the window uploaded from layer 0 and the upper layers).

## Retained images on the GPU

A photo drawn through ThorVG is scaled on the CPU in every frame, and on a phone that costs more than the rest of the frame (on a phone, about 24 ms for a full-screen 1080 × 2400 screenshot, against a budget of 8.33 ms). An image that stays the same from frame to frame can instead be drawn by the GPU from a texture that is uploaded once.

A program asks for this per image: `render::retained(image)` gives the image an identity (`Image::identity`, a shared `ImageIdentity`), and `draw_image` of an image with an identity goes to the GPU when the window can take it. Copies of the image share the identity, so the image must not change its pixels while it has one; a changed image is a new image and gets a new identity. An image without an identity is always drawn by ThorVG, as before.

How a frame is put together:

- The canvas puts what it draws into layers (`render::LayerPlan`). Everything starts in layer 0, the full-window ThorVG buffer. A retained image goes into the batch above the highest layer that has drawn something under it (its bounding box, inside the clip), and a later paint goes into the layer above the highest batch with an image under it, or into the layer of an earlier paint it overlaps. So a paint that does not overlap any image stays in layer 0 however late it comes, and a page of thumbnails with text between them stays in one layer.
- Each layer above 0 is a ThorVG canvas of its own, cut to the bounding box of what is in it (`Canvas::upper_layers()`): a top bar over a photo costs the bar's area, not a second full-window buffer. Clips are carried into each layer they are used in.
- `sdl3::Window::present` uploads the changed parts of layer 0 and of each upper layer ([damage tracking](#damage-tracking)) into their textures, then draws layer 0, the images of batch 0, layer 1, the images of batch 1, and so on. An image is drawn with `SDL_RenderGeometry` as a quad under its full transform (the zoom view's scale and position, the pager's offset), cut to the clip rectangle, with the opacity in the vertex colour.
- Textures are made the first time an image is drawn (the pixels are premultiplied on the way, so that linear filtering does not darken the edges of transparent areas, and drawn with `SDL_BLENDMODE_BLEND_PREMULTIPLIED`; the upper layers, which ThorVG writes premultiplied, are drawn the same way) and kept in `render::RetainedTextures`, keyed by the identity. The cache holds a weak reference to the identity, so a texture is dropped in the frame after its image is destroyed: the textures follow whatever store keeps the images. Beyond `WindowOptions::image_texture_bytes` (default `image_texture_bytes`), the least recently drawn textures are dropped as well, but never one drawn in the current frame. A lost device (`SDL_EVENT_RENDER_DEVICE_RESET`) drops them all.
- `Canvas::prefetch_image(image)` has the window make the texture of an image that is not drawn yet, so that the photo a swipe brings in next is uploaded while the finger is still.

The image is drawn by ThorVG instead when:

- the window has no GPU renderer (SDL's `software` renderer) or `Window::set_gpu_images(false)` / `WindowOptions::gpu_images = false` turned it off; a canvas without a window, as in the capture tool and the tests, always draws on the CPU;
- a path clip is active (a rounded rectangle, a Material shape): the GPU cuts only to a rectangle. A rectangle clip under rotation is cut to its bounding box, as ThorVG does;
- it is drawn at less than `retained_min_scale` of its size in either direction: SDL's renderer has no mipmaps, so a texture shrunk below half would alias where ThorVG averages. `Canvas::allow_minified_images()` lifts this limit until the next `restore()`, for pictures in motion such as a photo grid being pinched, where a few frames of aliasing cost less than drawing every picture with ThorVG (on the emulator, frames of over 100 ms);
- it is larger than the renderer's largest texture (`SDL_PROP_RENDERER_MAX_TEXTURE_SIZE_NUMBER`), or making its texture failed once;
- it would need more than `layers_max` layers.

Limits: the clip rectangle is rounded to whole pixels, where ThorVG antialiases a fractional clip edge. Filtering is bilinear (`image_texture_smooth`), the same as ThorVG's at the scales the GPU takes. ThorVG's sampler sits about half a source pixel off the image's geometry, so the same image drawn on the GPU lands up to about half a pixel up and to the left of where ThorVG put it; the GPU's position is the exact one. The image's pixels stay in memory next to the texture. The image must live until the frame is presented, since the window reads it in `present`.

The counts in [frame timing](#frame-timing): `gpu images` (images drawn as textures; `images` still counts all), `uploads` and `upload MB` (textures made in the frame), `layers` (ThorVG layers rasterized), and `textures` and `texture MB` (kept at the end of the frame). Making a texture is timed in `upload`; drawing the textures happens in `present`.

## Video frames on the GPU

A playing video changes its picture 24 to 60 times a second, so it cannot be a retained image, whose pixels must never change, and drawing it through ThorVG would convert and scale every frame on the CPU. `render::VideoFrame` (`lamina/render/video.hpp`) is a decoded frame as the decoder gives it: its size, `VideoLayout::nv12` (a luma plane and one plane of interleaved Cb and Cr) or `VideoLayout::i420` (three planes) or `VideoLayout::argb` (straight, not premultiplied ARGB in `argb`, one `std::uint32_t` per pixel, no padding; for animated images and anything else already in RGB), the planes with their pitches, the matrix (`VideoMatrix::bt601` or `bt709`) and whether it is full range. It also carries `surface`, an identity that stays the same for the whole video (`render::video_surface()`, made once per player), and `generation`, which the program raises for every new frame.

`Canvas::draw_video(frame, rect, opacity)` draws it stretched to the rectangle, under the transform and the clip, like `draw_image`:

- When the window can take it (`RetainedImageSink::accepts_video`), it is placed in the layers exactly as a retained image is ([Retained images on the GPU](#retained-images-on-the-gpu)), so it is not part of layer 0's fingerprints: a new frame changes no tile of the CPU buffer, and only what overlaps the video, such as a bar or a seek row drawn over it, goes into the upper layers. The window keeps one streaming texture per surface, in the format of the frame (`SDL_PIXELFORMAT_NV12` or `SDL_PIXELFORMAT_IYUV`) with the matching colorspace (`SDL_COLORSPACE_BT709_LIMITED` and so on), so the GPU converts to RGB while it draws; an ARGB frame gets an `SDL_PIXELFORMAT_ARGB8888` texture in `SDL_COLORSPACE_SRGB`, filled with `SDL_UpdateTexture` after premultiplying (every video texture blends premultiplied), and every GPU renderer takes it, so it needs no YUV format; it uploads the planes with `SDL_UpdateNVTexture` or `SDL_UpdateYUVTexture` only when the generation changes, so a paused video or one zoomed and panned between frames uploads nothing. A renderer that has only one of the two formats gets the planes rearranged into it on the way. The texture is dropped in the frame after the surface's last owner lets it go, and on a lost device.
- `retained_min_scale` does not apply: a 4K frame on a phone is drawn at about a quarter of its size, and the CPU path would convert and scale 8 Mpx in every frame (about 140 ms of `paint` per frame on the emulator, against about 2 ms on the GPU). Without mipmaps a frame drawn that small aliases where fine detail moves; for video that was taken as the lesser cost.
- Otherwise (no GPU renderer, `gpu_images` off, a path clip, no YUV format in the renderer) the canvas converts the frame to ARGB once per generation (`render::video_image`, with the coefficients in `lamina/tokens/video.hpp`; an ARGB frame is copied as it is) and draws that as a retained image, so a window that takes images but not videos still draws it on the GPU, at the cost of one texture per frame. The converted frames of the last `cpu_frames_kept` surfaces are kept, so a paused video is not converted again. On the CPU path a new generation is a new image, so its tiles are repainted.

`lamina/render/video.hpp` has no decoder: the program decodes, and hands each new frame over with a new generation.

The counts in [frame timing](#frame-timing): `video ups` and `video MB` (the video frames uploaded in the frame and their bytes). `gpu images` counts a video drawn on the GPU as well.

## Frame timing

`lamina/diagnostics/frame_stats.hpp` measures where a frame's time goes, for finding out why motion stutters on a device. It is off by default; while it is off the canvas counts nothing and no stage is timed (the window reads the clock only around its wait for events, as it does for the time step). `WindowOptions::frame_stats` (`diagnostics::FrameStatsSwitches{hud, log}`) turns it on at start and `Window::set_frame_stats` at any time; `Window::frame_probe()` is the `diagnostics::FrameProbe` that collects it. The examples take `--frame-stats on|log|off` (`on`: the overlay and the log; `log`: the log only), and the components gallery has a Frame timing toggle (the speed icon) under Theme on Basics, which turns both on.

Each frame is split into stages, each timed exclusively (a nested stage pauses the one around it): `wait` (the time `next_frame` slept waiting for an event, kept only for frames that follow the previous one closely, see below), `events` (polling SDL and converting the events, and measuring the window), `update` (the `update` callback), `layout` (marked by the program with `diagnostics::StageScope(probe, Stage::layout)`; the gallery marks its layout pass), `paint` (clearing the canvas and the `paint` callback, which builds the ThorVG scene), `image copy` (inside `draw_image`, the ThorVG canvas's `Picture::load` with its copy of the pixels), `raster update` (`SwCanvas::update`: ThorVG turns the paths into spans, cut to the rectangle being repainted), `raster draw` (`SwCanvas::draw` and `sync`: filling the 32-bit buffer inside the rectangles that [damage tracking](#damage-tracking) repaints, once per rectangle; with worker threads, `update` only hands the paths to the workers and the main thread waits for them in `draw` and `sync`, so compare the sum of the two), `upload` (`SDL_UpdateTexture` of the changed parts of the canvas, of the upper layers, and making the textures of retained images), and `present` (`SDL_RenderClear`, `SDL_RenderTexture` and `SDL_RenderPresent`, which waits for vsync). `work` is the sum of all stages but `wait` and `present`. A GPU driver may defer the texture upload into the present, so the stage boundaries between `upload` and `present` are what the CPU saw, not what the GPU did.

The canvas counts what each frame draws, in `render::Canvas`'s own methods so that every backend counts alike: paths and their points (`fill_path`, `fill_rect`, rounded rectangles, and text, which is drawn as one path of glyph outlines per line), `offscreen`, the paths, rectangles, text lines and icons whose bounding box lies wholly outside the canvas or its clips (they are skipped: text lines and icons before their outlines are built, so their points are not counted), blurred shadows (counted also when skipped), `shadow new`, the shadows the ThorVG canvas blurred in the frame because its cache did not have them, clips, `draw_image` calls and the image pixels they draw, and `cover Mpx`, the sum of the drawn shapes' bounding boxes inside the canvas (an estimate of overdraw, not the pixels ThorVG really touched, which it does not report). The ThorVG canvas adds the bytes it copies (`image MB`). A program can add `loads` and `load MB` (Gallery counts the decoded pictures it takes in a frame).

The frame interval is the time between the ends of two presents. A frame has an interval only if the wait before it was no longer than `idle_wait_refreshes` refresh periods, so the gap after an idle wait does not count, while frames driven by touch events (a drag, which does not animate by itself) do. A frame the program asked for with `wake_after` of at most `paced_wake_max_seconds` (0.1 s), such as the next frame of a playing video, also has its interval, and the timeout of that wake does not end a gesture, so a video paced at its own frame rate is one run, logged with a `running` line every `log_frames` frames, rather than a string of one-frame gestures; against a 60 Hz display, each frame of a 30 fps video counts as late with one missed refresh. A frame is late when its interval is longer than `late_factor` refresh periods; `missed` adds up, for every interval, the refresh periods it took beyond one (rounded). The refresh rate is the one SDL reports for the window's display (`SDL_GetCurrentDisplayMode`); the median interval is shown next to it, because a system can run the window at a lower rate than the display reports, and then every frame would look late against the reported rate. `Window::presented_seconds()` is the time, on SDL's tick clock in seconds, at which the last `present` came back from `SDL_RenderPresent` (empty before the first present), for a program that checks its own pacing, such as a video player comparing the times between presents with the times between the frames it showed. It is when the CPU handed the frame over, not when the display showed it.

`sdl3::paint_frame_stats(window, canvas, fonts, scheme, frame)` (`lamina_sdl3/frame_stats.hpp`) draws the overlay. A gesture ends when, while frame timing is on, no event comes for `idle_wait_refreshes` refresh periods after some recorded frames (the window first waits that long before waiting on as usual). With the `hud` switch on, the window then draws one more frame that is not recorded, the report frame, and only in that frame does `paint_frame_stats` draw anything; the measured frames never include the overlay's own drawing, and the overlay disappears with the next frame, such as the next touch. It summarizes the last run, the recorded frames since the last pause longer than `run_gap_seconds` (at most `recent_frames` of them), so that a fling and the fade of the scroll indicator after it count as one; a run of fewer than `log_min_frames` frames, such as a tap, keeps the previous summary. It is drawn in the corner `FrameStatsTokens::corner` of the safe area: a bar per frame of the last `recent_frames` frames (its interval, or its work for a frame with no interval; late ones in the error colour; the line is one refresh period), the interval average, median and worst, the late and missed counts against the refresh rate, the renderer, vsync, the window and canvas sizes in pixels, a table of each stage's average and worst and each count's average and worst, the worst frame's stages and counts, and the first `listed_late_frames` late frames with their interval, work, the stage that took longest and the loads in them. A program calls it at the end of its `paint`. An animation that never stops, such as an indeterminate progress indicator, never ends a gesture, so the overlay does not appear over it; the log still writes a `running` line every `log_frames` frames. The overlay does not keep the loop animating.

With the `log` switch the window writes the same report as one line under the tag `FrameStatsTokens::log_tag` (`lamina.frames`), to logcat at info level on Android and to stderr elsewhere: one `gesture` line when a gesture of at least `log_min_frames` frames ends, and a `running` line every `log_frames` frames while frames keep coming. `diagnostics::report_rows` and `report_line` make the text, and `diagnostics::paint_frame_hud` draws rows of it anywhere; the tokens are in `lamina/tokens/frame_stats.hpp`.

## Cursor

`input::Cursor` and `sdl3::Window::set_cursor` set the system cursor (arrow, text, pointer, horizontal and vertical resize, move, not allowed); widgets that want one report it through `cursor()`. `input::WheelEvent::shift` says whether Shift was held. `input::Key` also names F1 to F12, Insert, the Menu key and `Key::alt`, which the window reports when Alt is pressed and released alone; a `PointerEvent` carries the Shift and Ctrl states of a press or release, and a right press arrives as an `input::ContextClick` in `Frame::context`.

## Preference folder

`lamina_sdl3/resources.hpp`: `preference_directory(organization, application)` returns the folder where a program may keep its own files (`SDL_GetPrefPath`, which creates it: `%APPDATA%\<organization>\<application>\` on Windows) and throws an error with SDL's reason if there is none.

## Widget protocol

`lamina/widgets/protocol.hpp`: C++20 concepts for the shape the widgets share, one per capability. `Paintable` has `paint(canvas, scheme)`; `Steppable` has `step(dt)` and `animating()`; `HandlesPointer`, `HandlesKeys` and `HandlesText` have a `handle` overload for that event, whose result stays the widget's own (`bool`, `MenuResponse`, `DialogResult`); `Cancellable` has `cancel_interaction()`; `HoldsPointer` has `holds_pointer()`, true while the widget owns the current press (a slider being dragged, an open menu), so a scroll area around it does not take a touch drag. `Targeted` has `target_hit(event)`, how a control's 48 dp touch target is hit; `WidgetSet` and the containers of small controls use it to give the point to the nearest control where targets overlap. For size, `Sized` has `width()`, `height()` and `set_origin`; `WidthSettable` adds `set_width`; `SizeSettable` adds `set_size(width, height)`, which `Button` has; `Measurable` has `measure(constraints)` and `arrange(rect)`, as `Label`, `TextField` and `NavigationRail` do. `widgets::node(w)` in `nodes.hpp` is one adapter over them: a `Measurable` widget measures and places itself (a text field keeps its own width at its top left); otherwise a `WidthSettable` one takes the whole width; otherwise a `Sized` one keeps its size; both are centered vertically. `centered_node`, `full_width_node` and `measured_node` choose one of these placements directly, and `filled_node` gives a `SizeSettable` widget the whole rectangle it is placed in; `node` never picks that one, so a button stays its own size unless asked. The tests check with `static_assert` which concepts each widget satisfies.

## WidgetSet

`lamina/widgets/widget_set.hpp`: `WidgetSet` holds widgets of any kind that are `Paintable`, steps the `Steppable` ones, paints them all in the order they were added, and reports whether any of them is animating, so a `Label` can be in a set too. `add(widget)` refers to a widget that lives elsewhere; `emplace<W>(args...)` builds one inside the set and returns a reference that stays valid. `cancel_interaction()` reaches the members that have it. `add(widget, on_result)` and `emplace_with<W>(on_result, args...)` also take a handler, and `handle(PointerEvent)` and `handle(KeyEvent)` give the event to every member that takes it and call the member's handler with the widget's own result (a handler may take the widget too: `(W&, const Result&)`); they return true when a result says it used the event (`true`, or `consumed`). `remove(widget)` takes a widget out, and a widget built in the set is destroyed. Removing is safe while the set is going through its members, even from the widget's own handler: the widget is skipped from then on and leaves the set when the outermost pass ends, and a widget added during a pass waits for the next one. `for_each<W>(f)` goes through the members of type `W` in order, under the same rules, and `contains(widget)` tells whether a widget is in the set. `handle(TextEvent)` passes text to the members that take it, `set_enabled(bool)` enables or disables every member that can be (`Disableable`), and `accessible_nodes()` gathers their accessibility nodes. Otherwise the set does nothing else: the program decides where input goes (with `OverlayStack` and `FocusManager` below) and runs the layout. A program can keep several sets to paint something between them, as the navigation example paints the rail button between the page and the menus.

## Overlays

`lamina/widgets/overlay_stack.hpp`: `OverlayStack` routes input past menus and dialogs. `add_base(widgets...)` names what lies below every overlay: anything `Cancellable`, a `WidgetSet` too. An `Overlay` is a widget with `is_open()`, pointer and key `handle` and `cancel_interaction()`, such as `Menu`, `GroupedMenu` and `Dialog`. After opening one, the program calls `push(overlay, on_result)`; a modal push (the default) first cancels the interaction in progress on the overlays already open and on the base, so the button that opened a menu loses its hover. `handle(event)` gives a pointer, key or text event to the topmost open overlay, calls `on_result` with the widget's own result when `on_result` takes that type (menus, dialogs and the snackbar return one type for pointer and key events, `MenuResponse`, `GroupedMenuResponse`, `DialogResult` or `SnackbarResponse`, so one handler gets both), and returns true when the event stops there: always for a modal overlay, and for a modeless one (`Modality::modeless`) when the result says it used the event (`true`, or `consumed`). The event then goes on to the overlay below; when `handle` returns false, the program gives it to the base. An overlay that has closed leaves the stack by itself, right after the event that closed it. With `set_focus(focus_manager)`, a modal push also takes the keyboard focus away from the widgets below (`FocusManager::suspend`) and gives it back to the widget that had it when that overlay leaves (`resume`), unless the widget has left the order or cannot take the focus, or a pointer press closed the overlay: a press ends keyboard focus, so the remembered widget is then forgotten (`discard`); overlays stacked on each other give it back in order, and pushing an overlay again does not take it twice. Menus get this too. `remove(overlay)` takes an overlay off the stack whether it is open or not, giving the focus back as a close does; called from a result handler during `handle`, it takes effect when that event is done. Painting stays with the program, so a closing menu keeps fading out in the order it is painted. The navigation example routes its two menus and two dialogs this way. `handle(WheelEvent)` routes the wheel the same way, to the overlays that take it, such as a dialog with scrolling content.

## Focus

`lamina/widgets/focus_manager.hpp`: `FocusManager` keeps the Tab order of the `Focusable` widgets added to it (`focused()` and `set_focused`; a text field is one). The widgets keep their own focus, so a click on a field or Escape is seen at once. `handle(KeyEvent)` moves the focus to the next widget on Tab and to the previous one on Shift+Tab, wrapping at the ends, and returns true when it used the key; while nothing has the focus, Tab focuses the first widget and Shift+Tab the last. Ctrl+Tab is left to the program, except while the focused widget accepts tabs (`TabAccepting`, `accepts_tab()` true, such as a text field with `TextFieldOptions::accepts_tab`): then Tab is left to that widget, Shift+Tab still moves back, and Ctrl+Tab and Ctrl+Shift+Tab move forward and back, so the keyboard can always leave it. This is the `AcceptsTab` behavior of WinForms and WPF text boxes, and it keeps such a field from being a keyboard trap (WCAG 2.1 success criterion 2.1.2). A widget with `can_focus()` (`FocusGated`) is skipped while it returns false, for a control that is hidden for the moment. `move_focus(direction)` and `clear_focus()` do the same from code, `remove(widget)` takes a widget out of the order and `clear()` empties it. `suspend()` remembers the focused widget and drops the focus, and `resume()` gives it back to that widget if it is still in the order; they nest, and `clear()` keeps what was remembered, so a program may rebuild the order in between. `advance(direction)` moves like `move_focus` but stops at the ends instead of wrapping and returns false there, so an owner can chain several orders, as a dialog chains its content and its actions; `has_focus()`, `any_can_focus()` and `focused_bounds()` (for widgets with `bounds()`) report on the order. For a `TextInput` (a `Focusable` with `caret_area()` and `next_blink_seconds()`), `caret_area()` gives where the system IME should open, for `Window::set_text_input`, and `next_wake_seconds()` when the caret blinks next, for `Window::wake_after`; both are empty while nothing has the focus. `add_group(manager, shown)` puts another `FocusManager` in the order as one stop that Tab goes through member by member and skips while `shown` returns false, as the panes of the pane scaffolds are.

`lamina/widgets/focus_indicator.hpp`: keyboard focus for the controls. `Button`, `IconButton`, `Fab`, `Checkbox`, `Switch` and `RadioButton` are `Focusable` (`focused()`, `set_focused`) and take `handle(KeyEvent)`. While one has the focus, Space or Enter activates a button, an icon button (a toggle icon button toggles) or a FAB, and Space toggles a checkbox or a switch and selects a radio button. The result is true when the key activated the control, as `handle(PointerEvent)` returns true on a click, so a program reacts to both in the same way. A key with Ctrl and an auto-repeated key (`KeyEvent::repeat`) do nothing, so holding Space toggles once. The control acts on the key press, since the window reports no key release, and shows no pressed state for it. This focus belongs to the keyboard: a click never gives it, and a pointer press that reaches the control, anywhere in the window, takes it away (a press the program stops before its controls, such as one on a scroll bar, leaves it), so the indicator shows only after Tab, as Compose's focus-visible behavior does. A text field still takes the focus on a click, and its outline shows it. A focused control raises its state layer to the focus opacity (0.10) and draws the M3 focus ring: 3 dp of `secondary`, 2 dp outside the container, the switch's track or the 40 dp state-layer circle of a checkbox or radio button, following its corners (`tokens/focus.hpp`; sources in [docs/design-tokens.md](design-tokens.md)). The ring fades in and out on the fast effects spring. `FocusIndicator` is the piece these controls share: it keeps the focus, drops it on a press, raises the state layer and paints the ring. The tab row, navigation bar and rail, slider, menus, the snackbar's action and the examples' seed chips and fold toggle use it too (see their entries); `paint_inward` draws the ring inside a shape instead, for the tabs, menu items and the fold toggle.

`lamina/widgets/focus_stop.hpp`: `FocusStop` wraps a part of a composite widget, such as a picker's day grid, as a `Focusable`, `FocusGated` member of a `FocusManager`, and `forward_focus` makes one for a child widget that is only sometimes shown.

## Disabled state

`lamina/widgets/enablement.hpp`: the disabled state. `Button`, `IconButton`, `Switch`, `Checkbox`, `RadioButton`, `Slider` and `TextField` take `enabled` in their options and have `enabled()`, `set_enabled(bool)` and `can_focus()` (`Disableable`, `FocusGated`); tabs, navigation bar and rail items, menu items and grouped menu items take `enabled` per item (`set_tab_enabled`, `set_item_enabled`), and the rows have `set_enabled` for the whole row, which keeps each item's own setting for when the row is enabled again. A disabled control ignores the pointer and the keys, drops its press, hover and keyboard focus, and `FocusManager` skips it; the item rows skip disabled items for the arrow keys, Home, End, a click and the access keys, a menu opened from the keyboard focuses its first enabled item, and a row without an enabled item leaves the Tab order. The colors are the disabled colors of Compose's defaults (content in on-surface or on-surface-variant at 38 %, containers in on-surface at 10 % or 12 %; the switch and the slider handle composite theirs over surface; the list is in [docs/design-tokens.md](design-tokens.md)), and they fade on the default effects spring where Compose switches at once; a button's elevation moves to its disabled level on its spring where Compose snaps it. `Enablement` holds the state and the fade; `resolve(scheme, StateColor)` turns a `tokens::StateColor` (a role, an opacity and whether it is composited over surface, or over another role with `over`) into a color. The FAB has no disabled state, as in Compose.

## Accessibility

`lamina/widgets/accessibility.hpp`: every widget has `accessible()`, which returns an `AccessibleNode`: a role (button, toggle button, checkbox, radio button, switch, slider, tab list, tab, text field, label, menu, menu group, menu item, dialog, navigation, navigation item, progress indicator, status, tooltip, title bar), a name, the bounds in window coordinates, a state (enabled, focusable, focused, toggled on, off or mixed, selected, a value with its range, modal), a value and a description where they apply, and children for the item rows, menus, dialogs, the snackbar and the title bar; menus, dialogs, snackbars and tooltips return nothing while closed. Names come from the visible text; a control without any (an icon button, a FAB, or a button, tab or navigation item with only an icon) needs `accessible_name` in its options and throws `std::invalid_argument` without one, and checkboxes, switches, radio buttons and sliders take `accessible_name` as an option. A text field is named by its label, or else its placeholder, and reports its text as its value. `WidgetSet::accessible_nodes()` gathers the nodes of its members (`Accessible`), and `find_accessible`, `focused_accessible`, `visit_accessible` and `describe` search and print a tree. The title bar names its caption buttons from `TitleBarOptions::names` (`TitleBarNames`, English by default), which a program translates. The model is platform-neutral and not yet connected to a platform's accessibility API.

## Keyboard shortcuts

`lamina/widgets/shortcuts.hpp`: `KeyChord` (a key with Ctrl, Shift and Alt), `format_chord`, which writes one with the platform's `ShortcutFormat` from `lamina/tokens/shortcut.hpp` ("Ctrl+Shift+S" on Windows and Linux, "⌃⇧S" on macOS), and `ShortcutRegistry`, which holds commands by id with a chord, an action and an enabled flag and runs the one whose chord a key matches. `FocusManager::claims_key` says whether the focused widget keeps a key for itself (a text field's clipboard and undo keys), and `handle(event, focus)` runs a command only for the keys the focus does not claim.

## Drag gestures

`lamina/motion/velocity_tracker.hpp`, `anchored_draggable.hpp`, `lamina/tokens/drag.hpp`: the drag machinery of the sheets, drawers and rail. `VelocityTracker` is Compose's least-squares (`Lsq2`) tracker: it fits the last 100 ms of samples, forgets them after a 40 ms pause, and returns the slope at the newest one. `AnchoredDraggable<T>` holds an offset between named anchors: `press`, `move` (a drag starts past an 8 dp slop) and `release` (the velocity, clamped to 8000 dp/s), `fling` (Compose's `computeTarget`: the closest anchor without velocity, the next one in the fling's direction at or above the velocity threshold, otherwise the positional threshold decides), and `animate_to` on a spring (which keeps the release velocity) or a tween. `PointerEvent::time_seconds` gives the samples their time; the SDL window fills it from the event timestamps. `widgets::Pager` (`lamina/widgets/pager.hpp`) routes a horizontal swipe between pages the way `ScrollArea::route` routes a scroll: child first, with its axis in `waiting_scrollers` while it waits ([Pager](components/containers.md#pager)).

## Pinch gestures

`lamina/widgets/pinch.hpp`: `PinchRecognizer` turns `Frame::fingers` into a pinch, for a widget that scales something other than a picture, such as a photo grid's column count. It measures the fingers as `ZoomView` does: the centre is their mean, and the span is twice the mean distance from it on each axis, joined with `hypot`. Two fingers down claim the touch (`claimed()`, until the last finger lifts), so the app can stop the scroll, the tap and the long press that the first finger's pointer events started. The pinch begins only when the span has moved more than `span_slop` from where it was when the second finger came and is at least `min_span` (both from the zoom tokens by default, `pinch_options(tokens::zoom)`), so two fingers that move together do not pinch. `handle` returns `began` at that moment with scale 1 and the fingers' centre, then `moved` with the span over the span at the start and the centre, and `ended` with the last values when fewer than two fingers are left. A finger that joins or leaves during a pinch changes neither the scale nor the centre: the recogniser starts the span again from the new fingers and keeps the scale reached so far, and keeps the centre where it was by an offset. A cancelled finger ends the pinch as a lift does; `cancel()` forgets every finger. SDL's own `SDL_EVENT_PINCH_*` events are not used: SDL 3.4.10 sends them from Android's scale gesture detector over the same fingers (`SDLSurface.java`), from macOS and iOS and from Wayland and X11 touchpads, and not on Windows, where a precision touchpad's pinch comes to the app as Ctrl and the wheel.
