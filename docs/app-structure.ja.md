# アプリの組み立て

[English](app-structure.md) · [README](../README.ja.md#資料)

lamina-ui のプログラムがどう動くかを書きます。窓とその繰り返し、受け取る入力、部品のあいだで入力・フォーカス・読み上げを振り分ける仕組みです。いちばん小さなプログラムは [README](../README.ja.md#いちばん小さなプログラム) にあります。

## ターゲットと入力のイベント

ライブラリは CMake のターゲット三つに分かれていて、`src/` の下にターゲットごとのフォルダーがあります。バックエンドの別名 `lamina::thorvg` と `lamina::sdl3` はそのまま名前空間の名前で、本体の名前空間は `lamina` です。`src/lamina/` は本体（`lamina::lamina`：トークン・色・描画面の口・文字・図形・レイアウト・入力のイベント・部品）で、SDL3 も ThorVG も使いません。`src/lamina_thorvg/` は ThorVG で描く描画面（`lamina::thorvg`）、`src/lamina_sdl3/` は窓・設定のフォルダー・OS のフォント（`lamina::sdl3`）です。二つのバックエンドは本体だけに依存し、互いには依存しません。部品はポインター・キー・文字の入力とクリップボードを `lamina/input/`（`lamina::input`）の形で受け取り、それを作るのは SDL3 の窓です。`input::Key` には編集用のキー・英字・数字と、`+ - * / . % = ( ) ^ !` の文字のキーと、スペースキー（`Key::space`）があります。スペースキーは窓が Enter と同じく名前のあるキーとして知らせるので、`key_for_character` は空白の文字を割り当てません。Page Up と Page Down（`Key::page_up`・`Key::page_down`）もあります。`input::WheelEvent` はポインターの位置でのマウスホイールの回転で、単位はノッチです（タッチパッドでは端数になります）。`dy` が正なら終わりの方へ、`dx` が正なら右へ送ります。OS がホイールの向きを逆にしている設定でも同じです。`ctrl` は Ctrl を押していたかどうかです（Alt も押しているときは立ちません）。窓はこれを `Frame::wheel` に集めます。`input::FingerEvent` はタッチ画面の上の一本の指で、番号、`down`・`move`・`up`・`cancel`、dp の位置、時刻を持ちます。窓は SDL の指のイベントから、すべての指を `Frame::fingers` に集めます。位置は、SDL が最初の指からマウスのイベントを作るときと同じ方法で換算するので、最初の指とそのポインターのイベントは一致します。SDL がマウスやペンから作るタッチのイベントは入れません。ポインターのイベントは今までどおり最初の指をタッチとして運び、たいていの部品はそれで足ります。何本もの指を追う部品（`ZoomView` など）は `Frame::fingers` を読みます。窓は文字のキーを、そのときの Shift の状態で打たれる文字で知らせます（`input::key_for_character`）。そのため `*` は、US 配列では Shift+8、日本語配列では Shift+: です。テンキーからも同じキーになります。文字のキーは文字入力を始めずにキーのイベントとして届くので、かな入力の IME に取られません。逆向きに、英字・数字・文字のキーからその文字を得るのが `input::character_for_key` です（英字は小文字になります）。`KeyEvent` は Shift・Ctrl・Alt の状態（`shift`・`ctrl`・`alt`）を持ちます。Ctrl+Alt は配列によっては AltGr なので、Alt も押されているあいだ `ctrl` は立ちません。`PointerEvent` は、マウス・指・ペンのどれから来たか（`kind`）を持ちます。窓は SDL の指とペンのマウス番号から決めます。`PointerEvent::waiting_scrollers` は、部品のまわりで指のなぞりが遊びを越えるのを待っているスクロールの軸を表します。内側のスクロールは、それと合わない角度のなぞりを手放せます。`PointerEvent::margin_claimed` は、ほかの部品がその点をタッチの範囲で取ったことを表します。そのとき部品は、自分の見た目の範囲だけで判定します（[タッチの範囲](design-tokens.ja.md#タッチの範囲)）。窓は、指が残したカーソルの位置へ Windows が送るマウスの動きを止めます（`input::TouchEchoFilter`）。なので、最後に触った部品は、マウスが本当に動くまでホバーの見た目になりません（[指のあとのマウスのこだま](design-tokens.ja.md#指のあとのマウスのこだま)）。システムが取り上げたタッチはクリックになりません。SDL は取り消された指から、ふつうの左ボタンの離しを作ります（SDL 3.4.10 の `SDL_SendTouch` は `SDL_EVENT_FINGER_CANCELED` でも `SDL_EVENT_FINGER_UP` と同じく、指のイベントより先に離しを送ります）。そのため窓はタッチの離しをいったん止め、最初の指の離しか取り消しが届くのを待ちます（`input::TouchReleaseGate`）。指が離れたのなら `up` と `leave` を、取り消されたのなら `leave` だけを渡します。`leave` はどの部品もクリックなしにポインターが去ったものとして扱います。指のイベントが来ない離しは 1 フレーム後に渡します。Android で戻るのために画面の端からなぞると、こうなります。アプリはシステムが `ACTION_CANCEL` で取り上げるまでタッチを受け取ります（[Android](android.ja.md#動くもの)）。本体の中では、`tokens/` が値を入れる先のモジュール（`motion::SpringSpec`・`text::TextStyle`・`color::Role`・`render::CornerRadii`）に依存し、`motion/`・`text/`・`color/`・`render/` は `tokens/` に依存しません。

## 繰り返し

`lamina_sdl3/app.hpp`：`run_app` がその窓でフレームの繰り返しを回します。毎フレーム、フレームの情報（入力・大きさ・経過時間）を渡して `update` を呼び、`update` が返す背景色で描画面を塗りつぶして dp の縮尺に合わせ、`paint` を呼んで描かせてから画面に出します。`paint` はまだ動いているものがあるかどうかを返し、何も動いていなければ次のフレームはイベントを待ちます。なので `update` は、入力を処理したあとにもう一度配置をします。`Label::set_text` のように中身を変える処理は、次の配置で測り直す印を付けるだけです。何も動かないままフレームが終わると、次のイベントまで古い中身が出たままになります。押す・離す・外へ出るの三つが一つのフレームに届くタッチのタップがそうで、押下とホバーの層が動き始めません。ギャラリーと文字欄の例は、入力の前とあとの両方で配置をします。Windows では、窓の枠をドラッグしている間、システムの中で別の繰り返しが回ります。そのため、イベントを取り出して回すだけの繰り返しでは、マウスを離すまで描き直されず、離したときに配置が新しい大きさへ飛びます。`run_app` は、ドラッグ中に SDL が送る大きさ変更中の再描画のイベントごとにも、入力なしで 1 フレーム描きます（`Window::on_live_resize`）。そのため、中身が枠に合わせてついてきます。窓を `WindowOptions` と描画面から作る形と、作ってある `Window` を受け取る形があり、コールバックの中で窓を使うとき（クリップボード、`set_text_input`、`wake_after`）は後者を使います。`run_app` は例外を捕まえません。例外は呼び出し側に届き、報告のしかたは呼び出し側が決めます。フォントの読み込みのように繰り返しの前の準備で起きた例外も、同じ処理で扱えます。自分で繰り返しを書くときは、これまでどおり `Window` の関数をそのまま使えます。

## 窓

`lamina_sdl3/window.hpp`：描画面を映す SDL3 の窓。ポインターの位置を dp に直し、何も動いていない間はイベントを待って止まります（`lamina::sdl3`）。1 フレームの時間の刻みは 0.1 秒までですが、`wake_after` で頼んだ待ちの後だけは、待った時間をそのまま刻みに含めます。そのため、テキストフィールドのカーソルの点滅のように `step` で数える時間は、窓が止まっている間も進みます。窓は ThorVG に依存しません。描く先の描画面を `std::unique_ptr<render::Canvas>` で受け取り、毎フレーム `Canvas::resize` で窓の画素の大きさに合わせ、`Canvas::finish` が返す画素を 32 ビットの ARGB として画面に送ります。そのため、ARGB の画素に描く描画面であれば何でも差し込めます。`set_size(width, height)` は窓の中身の大きさを dp で変えます。最大化しているときは先に元に戻します。`set_minimum_size` は、利用者が枠を引いてそれより小さくできない大きさを dp で決めます。どちらもコンストラクターと同じく表示の倍率で dp を換算します。`set_always_on_top` は窓をほかの窓より手前に保ちます。`set_dark_system_bars(dark)` は、Android では、ステータスバーとナビゲーションバーのアイコンを、暗いアプリの上では明るく、明るいアプリの上では暗くします。ほかの OS では何もしません。`system_dark_theme()` は、システムがダークモードかどうかを返します（[Android](android.ja.md#システムのバー)）。Android では、システムの戻る操作が、`KeyEvent::back` を立てた `Key::escape` として届きます。使わなかったプログラムは `system_back()` を呼びます。これは戻る操作をシステムに渡し、タスクの根元のアクティビティならアプリを後ろへ回します（[Android](android.ja.md#戻る操作)）。ほかの OS では `KeyEvent::back` は立たず、`system_back` は何もしません。`native_handle` は、OS ごとのコードのために、Windows では窓の `HWND` を返します（ほかの OS では null）。見本は `examples::window_canvas()`（`examples/common/canvas.hpp`）が作る ThorVG の描画面を渡しています。`Frame::safe_area` は、システムのバーや画面の切り欠きがかからない窓の部分を、dp の余白として表したものです。デスクトップでは 0 です。Android ではアクティビティから受け取ります（`systemBars | displayCutout`）。SDL の安全な領域は、システムのジェスチャーの余白まで含むので使いません（[余白](android.ja.md#余白インセット)）。`Frame::gesture_insets` はシステムのジェスチャーの場所で、端のドラッグをそこから離すためのものです。配置には使いません。デスクトップと Android 11 より前では 0 です。換算（`safe_area_insets`・`insets_in_dp`）と `inset_rect` は `lamina/layout/safe_area.hpp` にあり、見本は安全な領域の内側に配置します。

## 描画面

`lamina/render/canvas.hpp`：曲線・角丸の四角・影・座標変換の積み重ねを持つ 2D の描画面。描くのは ThorVG です（`lamina::thorvg`）。ThorVG を選んだ理由は [docs/renderer-comparison.ja.md](renderer-comparison.ja.md) にあります。`fill_rect` はただの四角を塗り、バックエンドごとに実装します。ThorVG の描画面は `appendRect` を使わず、四角の曲線と同じ輪郭を渡します。ThorVG は軸にそろった4つの角の輪郭をなめらかにせずに塗るので、縁が変わってしまうためです。`draw_image(image, rect, opacity)` は `render::Image`（`render/image.hpp`：幅・高さと、行ごとに並べた ARGB の画素。アルファは乗算済みでないもの）を四角いっぱいに引き伸ばして描きます。座標変換とクリップに従い、不透明度は 0 から 1 です。Compose の `DrawScope.drawImage` に描き先の大きさとアルファを渡したときと同じです。ThorVG の描画面は呼ばれた時点で画素を写し取るので、画像を描画の終わりまで残しておく必要はありません。拡大縮小はバイリニアで補間します。GPU で描く身元のある画像は例外です（[GPU で描く画像](#gpu-で描く画像)）。`push_clip` は四角のほか任意の曲線も取ります。Compose の `Modifier.clip(shape)` と同じで、画像を Material の形に切り抜けます。`pop_clip` は最後のクリップを終え、クリップは入れ子にできます。`render/geometry.hpp` には点の計算（`+`・`-`・拡大・`length`・`unit`・`left_normal`・`cross`）と `circle_rect` があり、`render/path.hpp` は角丸の四角、枠線のための輪（`ring_path`）、円（`circle_path`）、点の列に沿って両端の丸い線の輪郭（`stroke_path`）を作ります。描画面は塗ることしかできないので、線もこの輪郭で塗ります。

描画面が省くもの：描画面は切り抜きの外接する長方形を持っています（四角の切り抜きはその四角、曲線の切り抜きはその外接する長方形を、座標変換をかけてから外側の切り抜きと重ねたもの。`visible_bounds()`）。`quick_reject(rect, outset)` は、今の座標での長方形を `outset` だけ広げたものが、それと描画面の外にまるごと出ているかを返します。`fill_path`・`fill_rect`・`fill_rounded_rect`・`fill_shadow`（ずれと、ぼかしの `shadow_margin_sigmas` 倍だけ広げる）・`draw_image` は、描くものの外接する長方形を座標変換の前に調べ、外ならバックエンドに渡しません。`text::draw_line` と `IconFont::draw` は、字形の輪郭を作る前に行やアイコンの箱（大きさの `cull_glyph_outset_em` 倍だけ広げる）を調べます。プログラムも `quick_reject` を呼んで、まとまった部分を飛ばせます。スクロールする領域はページ全体を毎フレーム描くので、長いページの大半はこれで飛ばされます。

ThorVG の描画面は、ぼかした影をキャッシュから描きます。ある形に初めて影を付けるとき、その形を ThorVG のガウスぼかし（`shadow_quality`）で専用の画像にぼかします。画像は四方に標準偏差の `shadow_margin_sigmas` 倍だけ大きく取ります。以後はその画像を描くので、ぼかしではなく画素を写すだけになります。キーは、左上の角から見た形（`1 / shadow_shape_steps` px に丸める）と、ぼかしと色です。なので、スクロールするページのように動くだけの影は一度しかぼかしません。画像はいちばん近い整数の画素の位置に描くので、影は面の端数の位置から最大で半画素ずれます。端数の位置に描くと、ThorVG は画像を拡大縮小する遅い道を通るためです。キャッシュは `shadow_cache_bytes` を超えた分を、描いたのが古い順に捨てます。今のフレームで描いた画像は捨てません。ThorVG はワーカーのスレッドを使います。数はコアの数より一つ少なく、多くて `worker_threads_max` です（`reserved_cores` がメインのスレッドのために残すコア）。トークンは `lamina/tokens/raster.hpp` にあります。

## 差分の描き直し

プログラムは毎フレーム窓の全体を描きますが、たいていのフレームで変わるのはその一部です。スクロールで動くのは一覧で、周りのバーは動きません。押したボタンで変わるのはそのボタンの画素です。動く写真は ThorVG ではなく GPU が描きます。そこで描画面は、層 0（窓いっぱいの ThorVG のバッファー）のうち、前のフレームから描くものが変わった部分だけを描き直し、窓はその部分だけを転送します。

仕組み：

- 窓を一辺 `damage_tile` px の正方形のタイルに分けます（`render::DamageGrid`、`lamina/render/damage.hpp`）。層 0 に届く呼び出し（`clear` の背景、`fill_path`、`fill_rect`、角の丸い長方形、`fill_shadow`、ThorVG で描く `draw_image`。文字とアイコンもこれらを通ります）は、それぞれ画素を決めるものからハッシュ（`render::Fingerprint`）にします。呼び出しの種類、座標変換の後の点、色と塗りの規則、影のずれ・ぼかし・色、画像の座標変換・不透明度・大きさと、身元（身元がなければ画素そのもの）、周りの切り抜き（座標変換の後の長方形やパスを外側から順に）のハッシュです。このハッシュを、呼び出しの外接する長方形の下にあるタイルすべてに、描いた順に混ぜ込みます。長方形はアンチエイリアスのために `damage_outset` px 広げ（影は整数の画素に置くので、さらに 1 px 広げます）、切り抜きと描画面の範囲で切ります。
- `finish` で、前に描き終えたフレームとハッシュが違うタイルを「変わったタイル」とします。動いた呼び出しは、出ていったタイルと入ったタイルの両方を変えるので、前の位置と今の位置の両方が描き直されます。GPU の画像の上の層へ移った呼び出しは層 0 から消えるので、前にいたタイルはそれなしで描き直されます。上の層の呼び出しと GPU で描く画像は、層 0 のハッシュに入りません。上の層はそれぞれ自分の格子を持ちます（下）。
- 変わったタイルは長方形にまとめます。まず各行で横に続くものをつなぎ、次に同じ列の範囲が縦に続くものをつなぎます。長方形が `damage_rects_max` 個より多いときは、つないでも増える面積がいちばん小さい二つを一つにすることをくり返します（横のつながりが `damage_merge_input_max` 個より多いときは、一度に全体を囲む一つにします）。ThorVG の描画面では、横のつながりはいつも行の全体にします（`Canvas::repaints_whole_rows`、`DamageSettings::whole_rows`）。なので長方形は、全幅の帯になります。ThorVG の CPU の描き込みは、半透明の区間を、16 バイト境界にそろう最初の画素までと、4 画素ずつのまとまりの後の残りは 1 画素ずつ、その間は 4 画素ずつまとめて混ぜ合わせます（`tvgSwRasterAvx.h`）。1 画素ずつのほうは `(c × (a + 1)) >> 8`、4 画素ずつのほうは `(c × a + 255) >> 8` で丸めるので、同じ画素でも 1 段階違うことがあります。長方形の左右の辺で区間を切ると、この切り替わる位置が動き、辺の隣の 3 画素までの色が変わりました（`components_capture --verify-repaint` で、行ごとに始まりのそろい方が違う幅 1081 px の描画面の、ダイアログの窓を覆う幕の下で見つかりました）。行の全体にすると、どの区間も全体を描いたときと同じになります。行を除いても残りの行が変わらないことは、試験と `--verify-repaint` の場面のどの比べでも確かめました。変わったタイルが全体の `damage_full_fraction` 以上なら、描画面の全体を描き直します。
- ThorVG の描画面は、フレームの場面をこれまでと同じように組み立てます。層 0 は専用の場面にまとめ、帯ごとに一度、`SwCanvas::viewport` をその帯にして描くので、ThorVG が塗るのはその行だけです。バッファーの残りは前のフレームのままです。`clear` の背景が不透明なら、背景が長方形を覆います。不透明でないときは、先に長方形を 0 にします。描画面は `EngineOption::None` で作るので、変わったと見た描画の範囲を自分で消す ThorVG の部分描画は働きません。また `draw(false)` で描きます。ThorVG の `draw(true)` は viewport に関係なくバッファー全体を消すので、`clear` が塗る背景と合わせて、前は毎フレームすべての画素を 2 回書いていました。
- 窓が最後に受け取ってから描き直した長方形は取っておきます（`Canvas::take_changed_pixels`。`damage_pending_max` 個を超えたら一つにまとめます）。`sdl3::Window::present` は、テクスチャのその部分だけを、長方形ごとに一回の `SDL_UpdateTexture` で、バッファーの行の幅を渡して転送します。上の層も中身の範囲に切り、同じように追います。層ごとに、その層のピクセルでの格子を持ちます。ピクセルでの範囲が前のフレームと同じ層は、バッファーをそのまま持ち続け、変わったタイルの帯を 0 にして（半透明なので）、`SwCanvas::viewport` と `draw(false)` で描き直します。層 0 と同じく層の行をまるごと描きます。描き直した部分は `UpperLayer::changed` で知らせ（窓のピクセルで。`take_changed_pixels` まで溜めます）、窓はそこだけを層のテクスチャへ転送します。範囲が変わったとき、前のフレームで描かれなかったとき、`resize` や `invalidate` のあと、差分の描き直しが切ってあるあいだ、窓がテクスチャを作ったときやリセットのあとですべてを転送するときは、層全体を描いて転送します。以前は上の層を毎フレームすべて描いて転送していたので、再生中の動画の上のスクリムは窓全体を層 1 に入れ、動画のコマごとに窓全体の ThorVG の塗りと 10 MB の転送がかかっていました（エミュレーターの横向きで 1 フレームの作業が約 9 ms。スクリムがなければ 2 ms 未満）。

全体を描き直すのは、最初のフレーム、`resize` の後（大きさや密度が変わったとき）、`Canvas::invalidate()` の後、差分の描き直しを切っている間の毎フレームです。窓がテクスチャ全体を転送するのは、テクスチャを作ったとき（最初のフレーム、大きさが変わったとき、デバイスを失ったとき）と、`SDL_EVENT_RENDER_DEVICE_RESET`・`SDL_EVENT_RENDER_TARGETS_RESET`・`SDL_EVENT_WINDOW_RESTORED`・`SDL_EVENT_DID_ENTER_FOREGROUND` の後です。GPU が中身をなくしたときのためです。テーマを切り替えると色が変わるので、すべてのタイルが変わります。アニメーションは、描いているタイルを変えます。

全体の描き直しを強制するには（差分の描き直しが同じ画素を描くか確かめるときや、時間を比べるとき）：

- 起動時は `WindowOptions::damage_tracking = false`、いつでも `Window::set_damage_tracking(false)`。窓のない描画面（試験やキャプチャーの道具）では `Canvas::set_damage_tracking`。既定は `lamina/tokens/raster.hpp` の `damage_tracking` です。
- 環境変数（名前は `full_repaint_environment`、`LAMINA_FULL_REPAINT`）を `0` と空以外の値にすると、そのプロセスのすべての窓で切ります。
- components の見本は `--full-repaint`、`components_capture` は `--full-repaint` と `--verify-repaint` を受け取ります（[テスト](testing.ja.md)）。

[フレームの計時](#フレームの計時)の数：`repaint tiles`（層 0 と上の層の変わったタイルの数。層全体を描き直したときはその層のすべてのタイル）、`repaint Mpx`（ThorVG が層 0 と上の層で描いた長方形の画素の数）、`canvas up Mpx`（窓が層 0 と上の層から転送した画素の数）。

## GPU で描く画像

ThorVG で描く写真は、毎フレーム CPU で拡大縮小されます。スマホではそれがフレームの残り全部より重くなります（実機で、画面いっぱいの 1080 × 2400 のスクリーンショットに約 24 ms。予算は 8.33 ms）。フレームをまたいで変わらない画像なら、一度だけ転送したテクスチャから GPU に描かせられます。

これは画像ごとにプログラムが頼みます。`render::retained(image)` は画像に身元（`Image::identity`、共有の `ImageIdentity`）を付け、身元のある画像の `draw_image` は、窓が受けられれば GPU に回ります。画像を写すと身元も共有されるので、身元のある画像は画素を変えてはいけません。変えた画像は別の画像で、新しい身元を付けます。身元のない画像は、これまでどおりいつも ThorVG で描きます。

1 フレームの組み立て：

- 描画面は、描くものを層に分けます（`render::LayerPlan`）。どれも初めは層 0、窓いっぱいの ThorVG のバッファーです。身元のある画像は、その下（切り抜きの中の外接する長方形）に何かを描いた層のうち一番上の層の上の組に入ります。後から描くものは、下に画像のある組のうち一番上の組の上の層か、重なる前の描画の層に入ります。なので、どの画像とも重ならない描画は、どれだけ後に来ても層 0 に残ります。サムネイルの間に文字のあるページも一つの層のままです。
- 層 0 より上の層は、それぞれ別の ThorVG の描画面で、中身の外接する長方形に切ってあります（`Canvas::upper_layers()`）。写真の上の上部バーなら、かかるのはバーの面積で、窓いっぱいのバッファーがもう一枚ではありません。切り抜きは、使われる層それぞれに持ち込みます。
- `sdl3::Window::present` は層 0 と各上の層の変わった部分を、それぞれのテクスチャへ転送します（[差分の描き直し](#差分の描き直し)）。それから層 0、組 0 の画像、層 1、組 1 の画像…の順に描きます。画像は `SDL_RenderGeometry` で、座標変換をそのままかけた四角形（ズームビューの倍率と位置、ページャーのずれ）として描き、切り抜きの四角で切り、不透明度は頂点の色に入れます。
- テクスチャは画像を初めて描くときに作ります（途中で画素を乗算済みにします。線形の補間で透明な部分の縁が暗くならないようにするためで、描くときは `SDL_BLENDMODE_BLEND_PREMULTIPLIED`。ThorVG が乗算済みで書く上の層も同じに描きます）。テクスチャは身元をキーに `render::RetainedTextures` に取っておきます。キャッシュは身元を弱い参照で持つので、画像がなくなった次のフレームでテクスチャも捨てます。テクスチャは画像を持っている入れ物に従います。`WindowOptions::image_texture_bytes`（既定は `image_texture_bytes`）を超えた分は、描いたのが古い順にも捨てます。今のフレームで描いたものは捨てません。デバイスを失ったとき（`SDL_EVENT_RENDER_DEVICE_RESET`）は全部捨てます。
- `Canvas::prefetch_image(image)` は、まだ描かない画像のテクスチャを先に作らせます。次にスワイプで入ってくる写真を、手が止まっている間に転送しておくためです。

次のときは ThorVG で描きます：

- 窓に GPU のレンダラーがない（SDL の `software`）か、`Window::set_gpu_images(false)` や `WindowOptions::gpu_images = false` で切ってあるとき。窓のない描画面（キャプチャーの道具や試験）は、いつも CPU で描きます。
- 曲線の切り抜き（角丸の四角、Material の形）の中のとき。GPU が切れるのは四角だけです。回転した四角の切り抜きは、ThorVG と同じく外接する長方形で切ります。
- どちらかの向きに `retained_min_scale` より小さく描くとき。SDL のレンダラーにはミップマップがないので、半分より縮めたテクスチャは、ThorVG が平均を取るところでちらつきます。`Canvas::allow_minified_images()` を呼ぶと、次の `restore()` までこの制限を外します。ピンチしている途中の写真の一覧のように動いている絵では、数フレームのちらつきのほうが、すべての絵を ThorVG で描くより安くつくからです（エミュレーターでは 100 ms を超えるフレームが出ました）。
- レンダラーの最大のテクスチャ（`SDL_PROP_RENDERER_MAX_TEXTURE_SIZE_NUMBER`）より大きいときと、テクスチャを作るのに一度失敗したとき。
- `layers_max` より多くの層が要るとき。

限界：切り抜きの四角は整数の画素に丸めます。ThorVG は端数のある切り抜きの縁をなめらかにします。補間はバイリニア（`image_texture_smooth`）で、GPU が受ける倍率では ThorVG と同じです。ThorVG の補間は画像の幾何から元の画素の約半分ずれているので、同じ画像を GPU で描くと、ThorVG の位置より最大で約半画素だけ左上に来ます。正しいのは GPU の位置です。画像の画素は、テクスチャとは別にメモリーに残ります。窓は `present` で画像を読むので、画像は表示し終わるまで残っていなければいけません。

[フレームの計時](#フレームの計時)の数：`gpu images`（テクスチャで描いた画像。`images` は全部を数える）、`uploads` と `upload MB`（そのフレームで作ったテクスチャ）、`layers`（走査した ThorVG の層）、`textures` と `texture MB`（フレームの終わりに取ってあるもの）。テクスチャを作る時間は `upload` に、テクスチャを描く時間は `present` に入ります。

## GPU で描く動画のコマ

再生中の動画は 1 秒に 24〜60 回絵が変わります。画素が変わってはいけない GPU に取っておく画像にはできず、ThorVG で描けば毎コマ CPU で変換して拡大縮小することになります。`render::VideoFrame`（`lamina/render/video.hpp`）は、デコーダーが渡したままのデコード済みのコマです。大きさ、`VideoLayout::nv12`（輝度の面と、Cb と Cr を交互に並べた面がひとつ）か `VideoLayout::i420`（三つの面）か `VideoLayout::argb`（`argb` に 1 画素 `std::uint32_t` ひとつずつ、詰めて並べた、アルファを掛けていない ARGB。動くアニメーション画像のように、はじめから RGB のもののため）、それぞれの面とその行の幅、行列（`VideoMatrix::bt601` か `bt709`）、全範囲かどうかを持ちます。さらに、動画のあいだずっと変わらない識別の `surface`（プレーヤーごとに一度 `render::video_surface()` で作ります）と、新しいコマごとにプログラムが増やす `generation` を持ちます。

`Canvas::draw_video(frame, rect, opacity)` は、`draw_image` と同じように、変換と切り抜きのもとで長方形いっぱいに描きます。

- ウィンドウが受け取れるとき（`RetainedImageSink::accepts_video`）は、GPU に取っておく画像とまったく同じように層に置きます（[GPU で描く画像](#gpu-で描く画像)）。なので層 0 の指紋には入りません。新しいコマが来ても CPU のバッファーのタイルはひとつも変わらず、動画の上に重なるもの（上に描いたバーやシークの行など）だけが上の層に入ります。ウィンドウは surface ごとにストリーミングのテクスチャをひとつ持ちます。形式はコマに合わせて `SDL_PIXELFORMAT_NV12` か `SDL_PIXELFORMAT_IYUV`、色空間もそれに合うもの（`SDL_COLORSPACE_BT709_LIMITED` など）にするので、RGB への変換は GPU が描きながら行います。ARGB のコマには `SDL_COLORSPACE_SRGB` の `SDL_PIXELFORMAT_ARGB8888` のテクスチャを使い、アルファを掛けてから `SDL_UpdateTexture` で入れます（動画のテクスチャはどれもアルファを掛けた形で重ねるため）。この形式はどの GPU のレンダラーも持つので、YUV の形式は要りません。面の転送（`SDL_UpdateNVTexture` か `SDL_UpdateYUVTexture`）は generation が変わったときだけなので、止めている動画や、コマのあいだに拡大や移動をしただけの動画は何も転送しません。二つの形式の片方しか持たないレンダラーには、面を並べ替えてから渡します。テクスチャは、surface の最後の持ち主が手放した次のフレームと、デバイスを失ったときに捨てます。
- `retained_min_scale` は当てません。スマートフォンでは 4K のコマを元の約 4 分の 1 で描くので、CPU で描けば毎コマ 8 Mpx を変換して縮めることになります（エミュレーターで 1 コマあたり `paint` に約 140 ms。GPU なら約 2 ms）。ミップマップがないので、そこまで小さく描いたコマは細かい模様が動くところでちらつきます。動画ではそちらを小さい代償としました。
- そうでないとき（GPU のレンダラーがない、`gpu_images` が切ってある、パスで切り抜いている、レンダラーに YUV の形式がない）は、キャンバスがコマを generation ごとに一度だけ ARGB に変換し（`render::video_image`、係数は `lamina/tokens/video.hpp`。ARGB のコマはそのまま写します）、それを GPU に取っておく画像として描きます。なので、画像は受け取れても動画は受け取れないウィンドウでも、コマごとにテクスチャをひとつ作る代わりに GPU で描けます。直近の `cpu_frames_kept` 個の surface の変換済みのコマは取っておくので、止めている動画を何度も変換しません。CPU で描くときは、新しい generation は新しい画像なので、そのタイルを描き直します。

`lamina/render/video.hpp` にデコーダーはありません。デコードはプログラムが行い、新しいコマを新しい generation と一緒に渡します。

[フレームの計時](#フレームの計時)の数：`video ups` と `video MB`（そのフレームで転送した動画のコマとそのバイト数）。GPU で描いた動画も `gpu images` に数えます。

## フレームの計時

`lamina/diagnostics/frame_stats.hpp` は、1 フレームの時間がどこで使われているかを測ります。実機で動きが引っかかる理由を調べるためのものです。既定では切ってあり、切ってある間は描画面は何も数えず、段階の時間も取りません（窓が時計を読むのは、時間の刻みのためにイベント待ちの前後で読むところだけです）。起動時に入れるのは `WindowOptions::frame_stats`（`diagnostics::FrameStatsSwitches{hud, log}`）、途中で入れたり切ったりするのは `Window::set_frame_stats` です。集めているのは `Window::frame_probe()` の `diagnostics::FrameProbe` です。例のプログラムは `--frame-stats on|log|off` を受け取ります（`on` は重ね表示とログ、`log` はログだけ）。components のギャラリーでは、Basics の Theme にある Frame timing のトグル（速度計のアイコン）で両方が入ります。

1 フレームは段階に分けて測ります。段階はそれぞれ排他で、内側の段階に入っている間は外側の時間を止めます。`wait`（`next_frame` がイベントを待って眠っていた時間。前のフレームに続いて来たフレームだけ数えます。下を参照）、`events`（SDL のイベントを取り出して変換し、窓の大きさを測る）、`update`（`update` の呼び出し）、`layout`（プログラムが `diagnostics::StageScope(probe, Stage::layout)` で印を付けたところ。ギャラリーはレイアウトの処理に付けています）、`paint`（描画面を塗りつぶし、`paint` を呼んで ThorVG の場面を組み立てる）、`image copy`（`draw_image` の中で、ThorVG の描画面の `Picture::load` が画素を写す）、`raster update`（`SwCanvas::update`：ThorVG がパスを走査線の区間に直す。描き直す長方形の範囲で切る）、`raster draw`（`SwCanvas::draw` と `sync`：32 ビットのバッファーのうち、[差分の描き直し](#差分の描き直し)で描き直す長方形の中を、長方形ごとに一度塗る。ワーカーのスレッドがあると、`update` はパスをワーカーに渡すだけで、メインのスレッドは `draw` と `sync` でワーカーを待つので、二つの合計で比べる）、`upload`（描画面の変わった部分と上の層の `SDL_UpdateTexture`、身元のある画像のテクスチャ作り）、`present`（`SDL_RenderClear`、`SDL_RenderTexture`、vsync を待つ `SDL_RenderPresent`）です。`work` は `wait` と `present` を除いた全段階の合計です。GPU のドライバーはテクスチャの転送を present まで遅らせることがあるので、`upload` と `present` の境目は CPU から見た区切りで、GPU が実際にしたことの区切りではありません。

描画面は、各フレームで描いたものを `render::Canvas` 自身のメソッドで数えます。なのでどのバックエンドでも数え方は同じです。パスとその点の数（`fill_path`、`fill_rect`、角の丸い長方形、文字。文字は 1 行ごとに字形の輪郭を一つのパスにして描きます）、`offscreen`（外接する長方形がまるごと描画面かその切り抜きの外にあるパス・四角・文字の行・アイコン。描かずに飛ばします。文字の行とアイコンは輪郭を作る前に飛ばすので、その点は数えません）、ぼかした影（飛ばしたものも数える）、`shadow new`（ThorVG の描画面のキャッシュになく、そのフレームでぼかした影）、切り抜き、`draw_image` の回数と描いた画像の画素数、`cover Mpx`（描いた図形の外接する長方形のうち描画面の中にある面積の合計。重ね塗りの見積もりで、ThorVG が実際に触った画素ではありません。ThorVG はそれを知らせません）です。ThorVG の描画面は写したバイト数（`image MB`）を足します。プログラムは `loads` と `load MB` を足せます（Gallery は、そのフレームで受け取ったデコード済みの絵を数えます）。

フレームの間隔は、二つの present の終わりの間の時間です。直前の待ちが `idle_wait_refreshes` 回分のリフレッシュより長くなかったフレームだけが間隔を持ちます。なので、しばらく何もなかった後の空白は数えず、タッチのイベントで進むフレーム（自分では動き続けないドラッグ）は数えます。プログラムが `paced_wake_max_seconds`（0.1 秒）以下の `wake_after` で求めたフレーム（再生中の動画の次のコマなど）も間隔を持ち、その待ちが切れても動作の終わりにはしません。なので、自分のコマの速さで進む動画は、1 コマずつの動作の連続ではなく一続きの走りになり、`log_frames` フレームごとに `running` の行を書きます。60 Hz のディスプレイに対しては、30 fps の動画のコマはどれも、リフレッシュを 1 回逃した遅れたフレームに数えます。間隔が `late_factor` 回分のリフレッシュより長いフレームが遅れたフレームです。`missed` は、各間隔が 1 回分を超えて使ったリフレッシュの回数（丸めたもの）の合計です。リフレッシュレートは、窓のあるディスプレイについて SDL が知らせる値（`SDL_GetCurrentDisplayMode`）です。その隣に間隔の中央値も出します。システムがディスプレイの値より低いレートで窓を動かすことがあり、そのときは知らせられた値に対してすべてのフレームが遅れて見えるためです。 `Window::presented_seconds()` は、最後の `present` が `SDL_RenderPresent` から戻った時刻です（SDL の tick の時計で秒。最初の present の前は空）。自分の進み方を確かめるプログラム、たとえば present の間の時間と表示したコマの間の時間を比べる動画プレイヤーのためのものです。CPU がフレームを渡した時刻であって、ディスプレイに映った時刻ではありません。

`sdl3::paint_frame_stats(window, canvas, fonts, scheme, frame)`（`lamina_sdl3/frame_stats.hpp`）は重ね表示を描きます。フレームの計時が入っている間、記録したフレームの後に `idle_wait_refreshes` 回分のリフレッシュのあいだイベントが来なかったら、操作がひと区切りしたとみなします（窓はまずそれだけ待ち、それから今までどおり待ちます）。`hud` が入っていると、窓はそこで記録しないフレームを 1 枚だけ描きます。これを報告のフレームと呼び、`paint_frame_stats` が何かを描くのはこのフレームだけです。なので測ったフレームに重ね表示を描く分は入りません。重ね表示は次のフレーム（次のタッチなど）で消えます。中身は最後のひと続きのまとめです。ひと続きとは、`run_gap_seconds` より長い休みの後に記録したフレームのことで（多くても `recent_frames` フレーム分）、はじきとその後のスクロールの目印が消えていく動きは一つに数えます。`log_min_frames` フレームに満たないひと続き（タップなど）では前のまとめのままです。場所は安全な領域の `FrameStatsTokens::corner` の隅です。中身は、直近 `recent_frames` フレームの 1 フレームごとの棒（間隔、間隔のないフレームは work。遅れたものはエラーの色。横線はリフレッシュ 1 回分）、間隔の平均・中央値・最悪、リフレッシュレートに対する遅れと取りこぼしの数、レンダラー、vsync、窓と描画面の画素の大きさ、段階ごとと数ごとの平均と最悪の表、いちばん遅いフレームの段階と数、遅れたフレームの最初の `listed_late_frames` 個（間隔、work、いちばん時間のかかった段階、その中の読み込みの数）です。プログラムは `paint` の最後でこれを呼びます。止まることのない動き（終わりのない進み具合の表示など）は操作の区切りにならないので、その上には重ね表示が出ません。ログはそれでも `log_frames` フレームごとに `running` の行を書きます。重ね表示は繰り返しを動かし続けません。

`log` が入っていると、窓は同じ報告を 1 行にしてタグ `FrameStatsTokens::log_tag`（`lamina.frames`）で書きます。Android では logcat に info の重さで、ほかでは標準エラーに出ます。`log_min_frames` フレーム以上の操作がひと区切りしたら `gesture` の行を 1 行、フレームが続いている間は `log_frames` フレームごとに `running` の行を書きます。文は `diagnostics::report_rows` と `report_line` が作り、`diagnostics::paint_frame_hud` はその行をどこにでも描けます。トークンは `lamina/tokens/frame_stats.hpp` にあります。

## 部品に共通する形

`lamina/widgets/protocol.hpp`：部品に共通する形を、できることごとに一つずつ C++20 のコンセプトで表します。`Paintable` は `paint(canvas, scheme)` を、`Steppable` は `step(dt)` と `animating()` を持ちます。`HandlesPointer`・`HandlesKeys`・`HandlesText` はその出来事を受け取る `handle` を持ち、その戻り値は部品ごとのまま（`bool`・`MenuResponse`・`DialogResult`）です。`Cancellable` は `cancel_interaction()` を持ちます。`HoldsPointer` は `holds_pointer()` を持ち、部品がいまの押下を持っている間（引きずっているスライダー、開いているメニュー）は true を返します。そのとき、まわりのスクロールする範囲は指のなぞりを引き取りません。`Targeted` は `target_hit(event)` を持ち、部品の 48 dp のタッチの範囲にどう当たったかを返します。`WidgetSet` と小さな部品をまとめる部品は、これを使って、範囲の重なるところではいちばん近い部品に点を渡します。大きさについては、`Sized` が `width()`・`height()`・`set_origin` を、`WidthSettable` はさらに `set_width` を持ちます。`SizeSettable` は `set_size(width, height)` を足したもので、`Button` が持ちます。`Measurable` は `measure(constraints)` と `arrange(rect)` を持ち、`Label`・`TextField`・`NavigationRail` がこれに当たります。`nodes.hpp` の `widgets::node(w)` は、これらに対する一つの変換です。`Measurable` な部品は自分で測って自分を置きます（入力欄は自分の幅のまま、左上に置かれます）。そうでなければ、`WidthSettable` な部品は幅いっぱいを取り、`Sized` な部品は自分の大きさのままで、どちらも上下の中央に置かれます。`centered_node`・`full_width_node`・`measured_node` を使えば、置き方を直接選べます。`filled_node` は `SizeSettable` な部品に、置かれた四角形をまるごと与えます。`node` はこの置き方を選ばないので、ボタンは頼まない限り自分の大きさのままです。どの部品がどのコンセプトを満たすかは、テストの `static_assert` で確かめています。

## WidgetSet

`lamina/widgets/widget_set.hpp`：`WidgetSet` は `Paintable` な部品を種類を問わずまとめて持ち、`Steppable` なものを進め、全部を加えた順に描き、どれかが動いているかを返します。そのため `Label` もセットに入れられます。`add(widget)` はよそにある部品を参照し、`emplace<W>(args...)` は部品をセットの中に作って、ずっと有効な参照を返します。`cancel_interaction()` はこれを持つ部品に伝えます。`add(widget, on_result)` と `emplace_with<W>(on_result, args...)` は受け手の関数も受け取ります。`handle(PointerEvent)` と `handle(KeyEvent)` は、その出来事を受ける部品すべてに渡し、部品自身の戻り値でその部品の受け手を呼びます（受け手は部品も受け取れます：`(W&, const Result&)`）。戻り値が出来事を使ったと示すとき（`true`、または `consumed`）に true を返します。`remove(widget)` は部品をセットから外し、セットの中に作った部品は壊します。セットが部品を順にたどっている最中に外しても安全で、その部品自身の受け手から外してもかまいません。外した部品はそれ以降飛ばされ、いちばん外側のたどりが終わったときにセットから抜けます。たどっている最中に加えた部品は、次のたどりから対象になります。`for_each<W>(f)` は型が `W` の部品を順にたどり、同じ決まりに従います。`contains(widget)` は部品がセットにあるかどうかを返します。`handle(TextEvent)` は文字を受ける部品に文字を渡し、`set_enabled(bool)` は無効にできる部品（`Disableable`）をまとめて有効・無効にし、`accessible_nodes()` は部品の読み上げ用の節点を集めます。それ以外のことはしません。入力の行き先を決めるのはプログラムで（下の `OverlayStack` と `FocusManager` を使えます）、配置もプログラムが行います。セットを複数持てば、その間に別のものを描けます。ナビゲーションの例では、ページの部品とメニューの間にレールのボタンを描いています。

## 重なるもの

`lamina/widgets/overlay_stack.hpp`：`OverlayStack` は、メニューやダイアログが開いているときの入力の行き先を決めます。`add_base(widgets...)` には、どの重なりよりも下にあるものを渡します。`Cancellable` なものなら何でもよく、`WidgetSet` も渡せます。`Overlay` は `is_open()`・ポインターとキーの `handle`・`cancel_interaction()` を持つ部品で、`Menu`・`GroupedMenu`・`Dialog` がこれに当たります。プログラムはそれを開いたあとに `push(overlay, on_result)` を呼びます。モーダルな `push`（既定）は、先に、すでに開いている重なりと下にあるものの操作の途中を取り消します。そのため、メニューを開いたボタンからはマウスを乗せた状態が消えます。`handle(event)` は、ポインター・キー・文字の出来事を、開いている重なりのいちばん上に渡します。`on_result` がその部品の戻り値の型を受け取れるときは、それを渡して呼びます（メニュー・ダイアログ・スナックバーは、ポインターとキーのどちらにも同じ型の `MenuResponse`・`GroupedMenuResponse`・`DialogResult`・`SnackbarResponse` を返すので、一つの関数が両方を受け取ります）。出来事がそこで止まるときは true を返します。モーダルな重なりなら必ず止まり、モードレスな重なり（`Modality::modeless`）なら、戻り値が出来事を使ったと示すとき（`true`、または `consumed`）に止まります。止まらなければ、出来事はその下の重なりに進みます。`handle` が false を返したら、プログラムが下にあるものに渡します。閉じた重なりは、閉じるきっかけになった出来事のすぐ後に、自分でスタックから外れます。`set_focus(focus_manager)` を呼んでおくと、モーダルな `push` は下にある部品からキーボードのフォーカスを取り上げ（`FocusManager::suspend`）、その重なりが外れるときに、もとの部品に返します（`resume`）。その部品が順から外れていたり、フォーカスを受けられなかったりするときは返しません。ポインターで押して閉じたときも返しません。押すことでキーボードのフォーカスは終わるので、覚えていた部品を忘れます（`discard`）。重なりが重なっているときは順に返し、同じ重なりをもう一度 `push` しても二重には取り上げません。メニューもこの扱いを受けます。`remove(overlay)` は、開いていても閉じていても重なりをスタックから外し、閉じたときと同じようにフォーカスを返します。`handle` の最中に受け手の関数から呼んだときは、その出来事が終わったときに外れます。描くのはプログラムの側なので、閉じかけのメニューは描く順のまま消えていきます。ナビゲーションの例は、二つのメニューと二つのダイアログをこの方法で扱っています。`handle(WheelEvent)` は、中身がスクロールするダイアログのようにホイールを受ける重なりへ、同じ決まりでホイールを渡します。

## フォーカス

`lamina/widgets/focus_manager.hpp`：`FocusManager` は、加えた `Focusable` な部品（`focused()` と `set_focused` を持つもの。入力欄がこれに当たります）の Tab の順を持ちます。フォーカスは部品自身が持つので、入力欄のクリックや Escape はすぐに反映されます。`handle(KeyEvent)` は、Tab で次の部品に、Shift+Tab で前の部品にフォーカスを移し、端では反対の端に戻ります。キーを使ったときは true を返します。どれにもフォーカスがない間は、Tab で最初の部品に、Shift+Tab で最後の部品にフォーカスを移します。Ctrl+Tab はプログラムに任せます。ただし、フォーカスのある部品がタブを受け取るとき（`TabAccepting`。`accepts_tab()` が true のもので、`TextFieldOptions::accepts_tab` にした入力欄が当たります）は、Tab をその部品に任せ、Shift+Tab では前へ移し、Ctrl+Tab と Ctrl+Shift+Tab で次と前へ移します。こうしてキーボードでいつでもその部品から出られます。WinForms と WPF のテキストボックスの `AcceptsTab` と同じ振る舞いで、キーボードが抜け出せなくなる罠を作りません（WCAG 2.1 の達成基準 2.1.2）。`can_focus()` を持つ部品（`FocusGated`）は、それが false を返す間は飛ばします。いまは隠れている部品のためです。`move_focus(direction)` と `clear_focus()` は同じことをコードから行い、`remove(widget)` は部品を順から外し、`clear()` は順を空にします。`suspend()` はフォーカスのある部品を覚えてフォーカスを外し、`resume()` はその部品がまだ順の中にあればフォーカスを返します。入れ子にでき、`clear()` しても覚えたものは残るので、その間にプログラムが順を作り直してもかまいません。`TextInput`（`caret_area()` と `next_blink_seconds()` を持つ `Focusable`）については、`caret_area()` がシステムの IME を開く場所を（`Window::set_text_input` に渡します）、`next_wake_seconds()` が次にカーソルが点滅する時刻を（`Window::wake_after` に渡します）返します。どちらも、フォーカスがない間は空です。`advance(direction)` は `move_focus` と同じように動きますが、端で先頭へ戻らずに止まり、false を返します。そのため、ダイアログが中身の順と操作のボタンをつなぐように、持ち主が複数の順をつなげられます。`has_focus()`・`any_can_focus()`・`focused_bounds()`（`bounds()` を持つ部品のとき）は順の状態を返します。`add_group(manager, shown)` は、別の `FocusManager` を一つの止まり場所として順に入れます。Tab はその中を一つずつたどり、`shown` が false を返す間は飛ばします。ペインの足場のペインはこれで入れます。

`lamina/widgets/focus_indicator.hpp`：操作部品のキーボードのフォーカスです。`Button`、`IconButton`、`Fab`、`Checkbox`、`Switch`、`RadioButton` は `Focusable`（`focused()` と `set_focused`）で、`handle(KeyEvent)` を受けます。フォーカスがある間、ボタン、アイコンボタン（切り替え式なら切り替わります）、FAB は Space か Enter で押され、チェックボックスとスイッチは Space で切り替わり、ラジオボタンは Space で選ばれます。キーで押されたときは true を返します。`handle(PointerEvent)` がクリックで true を返すのと同じなので、プログラムはどちらにも同じように応じられます。Ctrl を伴うキーと、押し続けたときに繰り返されるキー（`KeyEvent::repeat`）では何も起きません。Space を押し続けても、切り替わるのは一度だけです。ウィンドウはキーを離したことを伝えないので、部品はキーを押した時点で動き、押された見た目にはなりません。このフォーカスはキーボードのためのものです。クリックではフォーカスを受けず、部品に届いたポインターの押下では、窓のどこを押してもフォーカスを失います（スクロールバーの上などで、プログラムが部品に届く前に止めた押下では失いません）。そのため、フォーカスの表示は Tab の後にだけ出ます。Compose の focus-visible（※キーボード操作のときだけフォーカスを見せる仕組み）と同じ振る舞いです。入力欄は今まで通りクリックでフォーカスを受け、枠線でそれを示します。フォーカスのある部品は、状態の重ねをフォーカスの不透明度（0.10）に上げ、M3 のフォーカスの輪を描きます。`secondary` の 3 dp の輪を、入れ物、スイッチのトラック、またはチェックボックスとラジオボタンの 40 dp の状態の重ねの円から 2 dp 外側に、その角に沿って描きます（`tokens/focus.hpp`。出典は [docs/design-tokens.ja.md](design-tokens.ja.md)）。輪は速い効果のばねで現れ、消えます。これらの部品が共通に使うのが `FocusIndicator` で、フォーカスを持ち、押されたら手放し、状態の重ねを上げ、輪を描きます。タブの列・ナビゲーションバーとレール・スライダー・メニュー・スナックバーの操作、例の色の丸と折りたたみもこれを使います（それぞれの項を見てください）。`paint_inward` は輪を形の内側に描き、タブ・メニューの項目・折りたたみで使います。

`lamina/widgets/focus_stop.hpp`：`FocusStop` は、ピッカーの日のます目のような複合部品の一部を、`Focusable` で `FocusGated` な `FocusManager` の一員にします。`forward_focus` は、出ているときだけ止まる子の部品のための `FocusStop` を作ります。

## 無効の状態

`lamina/widgets/enablement.hpp`：無効の状態。`Button`・`IconButton`・`Switch`・`Checkbox`・`RadioButton`・`Slider`・`TextField` は、選択肢に `enabled` を取り、`enabled()`・`set_enabled(bool)`・`can_focus()` を持ちます（`Disableable`、`FocusGated`）。タブ・ナビゲーションバーとレールの項目・メニューの項目・まとまりに分けたメニューの項目は、項目ごとに `enabled` を取り（`set_tab_enabled`、`set_item_enabled`）、列には列全体を有効・無効にする `set_enabled` があります。列を有効に戻すと、項目ごとの設定がそのまま生きます。無効な部品はポインターとキーを受けず、押した状態・ポインターの重なり・キーボードのフォーカスを手放し、`FocusManager` はその部品を飛ばします。項目の並ぶ部品は、矢印・Home・End・クリック・アクセスキーで無効な項目を飛ばし、キーボードで開いたメニューは最初の有効な項目にフォーカスを置き、有効な項目のない列は Tab の順から外れます。色は Compose の既定の無効の色です（中身は on-surface か on-surface-variant の 38 %、入れ物は on-surface の 10 % か 12 %。スイッチとスライダーのつまみは surface の上に重ねた色。一覧は [docs/design-tokens.ja.md](design-tokens.ja.md)）。Compose は一度に切り替えますが、lamina-ui は既定の効果のばねで移します。ボタンの高さも、Compose は一度に変えますが、lamina-ui はばねで無効の高さへ移します。`Enablement` が状態と移り変わりを持ち、`resolve(scheme, StateColor)` は `tokens::StateColor`（役割・不透明度・surface の上に重ねるかどうか、または `over` でほかの役割の上に重ねること）を色にします。FAB には Compose と同じく無効の状態がありません。

## 読み上げ

`lamina/widgets/accessibility.hpp`：どの部品も `accessible()` を持ち、`AccessibleNode` を返します。中身は、役割（ボタン・切り替えボタン・チェックボックス・ラジオボタン・スイッチ・スライダー・タブの列・タブ・入力欄・ラベル・メニュー・メニューのまとまり・メニューの項目・ダイアログ・ナビゲーション・ナビゲーションの項目・進み具合の表示・状況の表示・ツールチップ・タイトルバー）、名前、窓の座標での位置と大きさ、状態（有効・フォーカスを受けるか・フォーカスがあるか・オン／オフ／途中・選ばれているか・値とその範囲・モーダル）、当てはまるときの値と説明、項目の並ぶ部品・メニュー・ダイアログ・スナックバー・タイトルバーでは子の節点です。メニュー・ダイアログ・スナックバー・ツールチップは、閉じている間は何も返しません。名前は見えている文字から取ります。見える文字のない部品（アイコンボタン・FAB・アイコンだけのボタン・タブ・ナビゲーションの項目）は選択肢に `accessible_name` が要り、ないと `std::invalid_argument` を投げます。チェックボックス・スイッチ・ラジオボタン・スライダーも選択肢で `accessible_name` を取ります。入力欄の名前はラベルで、ラベルがなければ案内の文字です。値には入力した文字を返します。`WidgetSet::accessible_nodes()` は部品（`Accessible`）の節点を集め、`find_accessible`・`focused_accessible`・`visit_accessible`・`describe` で木を探したり書き出したりできます。タイトルバーは、右上のボタンの名前を `TitleBarOptions::names`（`TitleBarNames`。既定は英語）から取るので、プログラムが訳を渡せます。この仕組みは OS に依らず、まだどの OS の読み上げの仕組みにもつないでいません。

## キーボードショートカット

`lamina/widgets/shortcuts.hpp`：`KeyChord`（キーと Ctrl・Shift・Alt）、それを `lamina/tokens/shortcut.hpp` のプラットフォームの `ShortcutFormat` で書く `format_chord`（Windows と Linux では「Ctrl+Shift+S」、macOS では「⌃⇧S」）、組み合わせ・動作・有効かどうかを持つコマンドを ID で保ち、キーに一致するものを走らせる `ShortcutRegistry`。`FocusManager::claims_key` はフォーカスのある部品がキーを自分のものにするか（テキスト欄のクリップボードと元に戻すキー）を返すので、`handle(event, focus)` はフォーカスが自分のものにしないキーだけでコマンドを走らせます。

## ドラッグ

`lamina/motion/velocity_tracker.hpp`・`anchored_draggable.hpp`・`lamina/tokens/drag.hpp`：シート・ドロワー・レールのドラッグのしくみ。`VelocityTracker` は Compose の最小二乗（`Lsq2`）の速さの測り方です。直近 100 ms のサンプルに式を当てはめ、40 ms 止まるとサンプルを忘れ、いちばん新しいサンプルでの傾きを返します。`AnchoredDraggable<T>` は、名前の付いたアンカーの間の位置を持ちます。`press`・`move`（8 dp の遊びを越えるとドラッグが始まります）・`release`（速さは 8000 dp/s までに抑えます）・`fling`（Compose の `computeTarget`。速さがなければいちばん近いアンカー、速さのしきい値以上ならはじいた向きの次のアンカーで、それ以外は位置のしきい値で決めます）と、ばね（離したときの速さを引き継ぎます）かトゥイーンで動かす `animate_to` があります。サンプルの時刻は `PointerEvent::time_seconds` で渡し、SDL の窓は出来事の時刻からこれを埋めます。`widgets::Pager`（`lamina/widgets/pager.hpp`）は、`ScrollArea::route` がスクロールを振り分けるのと同じやり方で、ページの間の横のなぞりを振り分けます。出来事はまず中身に渡し、待っている間は自分の軸を `waiting_scrollers` に記します（[ページ送り](components/containers.ja.md#ページ送り)）。

## ピンチ

`lamina/widgets/pinch.hpp`：`PinchRecognizer` は `Frame::fingers` からピンチを取り出します。写真の一覧の列の数のように、絵そのものではないものを指で拡大・縮小する部品のためのものです。指の測り方は `ZoomView` と同じで、中心は指の位置の平均、広がりは中心からの距離の平均を軸ごとに 2 倍して `hypot` で合わせたものです。2 本目の指が触れた時点で、その触れ方を引き取ります（`claimed()`。最後の指が離れるまで）。アプリはこれを見て、1 本目の指のポインターの出来事で始まったスクロール・タップ・長押しを止められます。ピンチが始まるのは、2 本目の指が触れたときから広がりが `span_slop` より大きく変わり、しかも `min_span` 以上あるときだけです（どちらも既定ではズームのトークンから取ります。`pinch_options(tokens::zoom)`）。そのため、2 本の指をそろえて動かしてもピンチにはなりません。`handle` はその時点で倍率 1 と指の中心を付けて `began` を返し、その後は始まったときの広がりに対する今の広がりの比と中心を付けて `moved` を返し、指が 2 本より少なくなると最後の値を付けて `ended` を返します。ピンチの途中で指が増えても減っても、倍率と中心は動きません。新しい指の組で広がりを測り直し、それまでの倍率を引き継ぎ、中心はずれの分を足して元の位置に保ちます。取り消された指は、離した指と同じくピンチを終えます。`cancel()` はすべての指を忘れます。SDL 自身の `SDL_EVENT_PINCH_*` は使いません。SDL 3.4.10 はこれを、同じ指から Android の拡大縮小の検出器で（`SDLSurface.java`）、また macOS・iOS と Wayland・X11 のタッチパッドから送り、Windows では送りません。Windows のプレシジョンタッチパッドのピンチは、Ctrl とホイールとしてアプリに届きます。
